# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

Zorvo (formerly Agent Desktop) is a macOS Tauri 2 app that hosts other coding agents. Qwen Code, Claude Code, Codex and the other agents come from the ACP registry and are driven over the Agent Client Protocol (ACP, JSON-RPC over stdio) and shown as a chat UI. Pi comes through the registry's `pi-acp` adapter. A PTY is used to run an agent's own terminal sign-in and the shells of the workspace terminal. React 19 + Tailwind 4 frontend in `src/`, Rust backend in `src-tauri/` (crate `zorvo`, lib `zorvo_lib`). Package manager is pnpm; Node comes from `.nvmrc` (26), which CI and the release workflow also read.

## Commands

```bash
pnpm install
pnpm tauri dev              # run the app (Vite on :1420 + Rust backend)
pnpm lint                   # tsc --noEmit + eslint --max-warnings=0
pnpm test                   # all Vitest tests
pnpm vitest run src/test/persistence.test.ts          # one file
pnpm vitest run src/test/persistence.test.ts -t "name" # one test
pnpm design-system          # local design-system reference on :5180
pnpm registry:update        # refresh the bundled ACP registry history (src-tauri/resources/registry-history.json)
pnpm cua-driver:fetch       # fetch the pinned computer-use driver into src-tauri/binaries/ (tauri dev and build run it)
pnpm cua-driver:update      # by hand: pin the newest cua-driver at least 7 days old and not below 0.52.1; read the diff
pnpm tauri build            # production bundle (the only build that applies the CSP); signs the update package, so it needs TAURI_SIGNING_PRIVATE_KEY (+ _PASSWORD) or --config '{"bundle":{"createUpdaterArtifacts":false}}'
node scripts/sign-release.mjs vX.Y.Z   # on the maintainer's Mac, in a clean checkout of the tag, after its Release run is green: sign and fill the draft release (see `docs/development.md`, "Releasing"); --dry-run writes nothing; run it with node, not pnpm (pnpm run puts node_modules/.bin first on PATH)
pnpm clean:rust             # cargo clean for src-tauri (empties the shared target, see "Working in worktrees")
```

Rust (from `src-tauri/`; `pnpm build` must have produced `dist/` first, since Tauri embeds it at compile time):

```bash
cargo fmt --check
cargo clippy --all-targets -- -D warnings
cargo test
cargo test --test it acp_manager_test::            # one integration test file
cargo test --test it acp_manager_test::some_name   # one test
```

Integration tests are modules of one binary, `tests/it/main.rs` (a new file needs a `mod` line there), so they share a process and run in parallel threads. A test that sets process-wide state gets its own file in `tests/`, like `installer_state_test.rs`.

The Rust ACP tests spawn `src-tauri/tests/fixtures/fake_acp_agent.mjs` with Node, so Node must be on PATH. Its flags add capabilities on top of its defaults (`loadSession`, `fork`, `delete`): `FAKE_ACP_RESUME` (`session/resume`), `FAKE_ACP_LIST` (`session/list`), `FAKE_ACP_LIST_PAGES` (pages from a JSON file), `FAKE_ACP_LIST_FAIL_AT=<n>`, `FAKE_ACP_CALL_LOG` (every method received, one per line), `FAKE_ACP_SUBAGENT=qwen|claude` (a prompt `subagent` sends a subagent's tool call and text marked with their parent in that agent's `_meta` shape), `FAKE_ACP_SLOW_REPLAY` (a load replay that pauses mid-way) and `FAKE_ACP_WRITE_FILES` (a JSON object of relative paths and contents, written into the session's folder when a `permission` prompt is answered allow, and by `crash` just before it exits) and `FAKE_ACP_SETUP_METHOD` (also offers Qwen Code's older terminal method, which marks an interactive setup), `FAKE_ACP_PARAMS_LOG` (appends `{method, mcpServers}` for every `session/new`, `session/load`, `session/resume` and `session/fork`) and `FAKE_ACP_MCP_CALL` (JSON `{tool, args}`) with `FAKE_ACP_MCP_LOG` (a prompt `mcp` makes the agent act as an MCP client: it spawns the first `mcpServers` entry its session was opened with, runs `initialize`, `tools/list` and that `tools/call`, logs each result and says `mcp:<text>`, or `mcp:none` when the session had no server), `FAKE_ACP_CHILD_PID_FILE` (at start, starts a child that ignores TERM and writes its pid there), `FAKE_ACP_ENV_LOG` (at start, one JSON line saying which of `ZORVO_MCP_SOCKET`, `ZORVO_MCP_TOKEN` and `ZORVO_TOOLS` are set, never their values) and `FAKE_ACP_TOOLS_COMMAND` (JSON `{tool, args}`, with `FAKE_ACP_MCP_LOG`: a prompt `tools` makes the agent run the program in `ZORVO_TOOLS` as `tools <tool> <json>` and log `{status, stdout, stderr}`). CI runs all of the above except `cargo fmt` (lefthook runs that pre-commit if installed with `pnpm lefthook install`).

## Architecture

**Frontend ↔ backend.** The UI calls Tauri commands (all registered in `src-tauri/src/lib.rs`'s `generate_handler!`) and listens to events: `acp-event` (one channel for every ACP session, payload `{sessionId, kind: update|permission|elicitation|elicitation-complete|turn-end|exit, ...}` built in `acp/commands.rs`) and `sign-in-terminal` (output and exit of an agent's terminal sign-in, see below).

**Browser.** `src-tauri/src/browser/` owns native WebKit views outside Tauri IPC, with one non-persistent store per session and separate configurations per tab. `browser_commands.rs` distinguishes manual UI actions from authenticated agent requests: browser access has a memory-only session grant, and uploads need a separate one-time destination/files approval. `browser_debug.rs` supervises a Node worker and installed Chrome/Brave in a temporary isolated profile for the advanced tools (`resources/browser-cdp/`). Regular Chromium diagnostics use a CDP pipe; explicit optional Lighthouse audits temporarily use a loopback DevTools port. Chromium and WebKit do not share pages or cookies. `browser` and `browser_guide` join the seven existing tools. Closing a session or exiting releases views and workers. BrowserPanel is an ordinary Inspector tab; its retained child view moves on bounds changes, with native scrolling and no screenshot/message pump. Main Tauri content keeps its existing network CSP. Separate browser pages load user/agent-selected HTTP(S) destinations and their subresources; address-bar search text goes to Google only on submission. Optional Lighthouse tools install from npm with a pinned lockfile on explicit user action. The design note/probe evidence in `docs/superpowers/specs/` and `experiments/browser-wk/` still state older-OS and integration coverage limits.

**Session engine.** Every session is an ACP chat, run by `src/hooks/session-engine/useAcpEngine.ts`. ACP updates are folded into chat messages by `src/lib/acp-events.ts`; modes/models/config options come from the agent at session start (`useAcpSessions.ts`, `lib/acp-draft.ts`). Saved terminal sessions from older versions are dropped on load (`dropTerminalSessions` in `lib/persistence.ts`).

**Agent profiles are the trust boundary.** ACP agents come from `src-tauri/src/registry/`: the official ACP registry, fetched by the Rust backend (never the webview) at startup when the last fetch is over 24 hours old and on **Check again**. It keeps a dated version history, and a version is offered only after it has been listed for 7 days. A history is bundled with each release (`pnpm registry:update` regenerates `src-tauri/resources/registry-history.json`). Agents in use are `settings.enabledAgents`, the version in use is `settings.agentVersions`, and installed agents are enabled once automatically (`withAutoEnabled`; never an npx agent, since a global npm package is not what Zorvo runs). Settings' **Check again** lives in the Agents section. The webview only ever sends an agent id (and folder); `acp/commands.rs::launch_for` turns the id into a command line. Never let the UI pass a raw command or args. An entry may offer several distribution kinds (`binary` plus `npx`, as kilo and sigit do); `registry/schema.rs::choose_distribution` picks one at parse time, so everything downstream still sees one `Distribution` per entry (the history stores only the chosen kind). Preference: a pinned `npx` package, then a pinned `uvx` package, then a binary with a build for this Mac and a valid checksum, then a binary with no build for this Mac (shown as unsupported). A package comes first because it does not depend on this Mac's platform (the choice frozen in the history is the same everywhere), because a binary is first looked up on `PATH` by its program name (`binary_program` in `resolve.rs`) and an unrelated program of that name would run as the agent, and because Zorvo may not unpack a binary's archive format. Each candidate must pass `is_valid_entry` unchanged: the choice only picks among valid candidates and a candidate that fails contributes nothing (no args, no env). One rule is looser than before, on purpose: a missing or `null` `sha256` on a platform other than this Mac's no longer drops the whole entry (`sha256_or_empty`; only `current_platform()`'s target is ever read, and an empty checksum never validates), and each kind of an entry is read on its own, so one malformed kind cannot hide a valid one. `RegistryEntry`'s derived `Deserialize` is for Zorvo's own files only and must never read raw registry data. An entry that fails every candidate is not offered but reported as unavailable (`UnavailableAgent`, reason `no_checksum` when this Mac's binary publishes no valid checksum, else `invalid_entry`; entries with no usable or a reserved id are left out of both lists).

**Agent catalog.** Settings → Agents and the welcome screen (`components/Onboarding.tsx`, its rules in `lib/onboarding.ts`: rows in use or on this Mac first, then the popular ones, five until Show all; ticking only puts the agent in use (`withAgentAdded`), a ticked agent that is not installed shows Install, which calls `addAgent`, and unticking only takes the agent out of use and cancels its install) read one read model: `get_agent_catalog` returns `Catalog::catalog_view` (in `registry/mod.rs`; its types are in `registry/catalog_view.rs`) with each registry agent's availability (including `unsupported` for a binary agent with no build for this Mac's target), install state and offered update. Recorded versions under 7 days old are ignored. `update_agent` (`installer/commands.rs`) is the only way an agent's version changes; the target comes from `Catalog::update_target`, never the UI. Logos: `registry/icons.rs` fetches SVGs from the registry CDN into the app data dir (only allowed URLs, SVG bodies only) and `get_agent_icons` returns data URLs, falling back to the bundled `src-tauri/resources/registry-icons.json` (`pnpm registry:update --icons-only` regenerates it). Frontend: `components/agents/` (`AgentCatalog`, `AgentCatalogRow`, `AgentCatalogPanel`), `hooks/useAgentCatalog.ts`, `useAgentCatalogActions.ts`, `useAgentUpdates.ts` (badge, and `settings.notifiedUpdates` for the once-per-version notice), `lib/agent-catalog.ts`, `lib/agent-icons.ts`. `AgentCatalog.unavailable` lists what the registry offers but Zorvo cannot (`parse_registry_report` output, kept in `registry-cache.json` as `unavailable`, `CatalogState::unavailable_agents`: sorted and deduped by id when stored, not in `agents`, no install or add path, and an id the history already has stays a normal row; a cache without the field counts as stale, so the next start fetches again). The UI shows it as a collapsed "Not available (N)" section (`components/agents/UnavailableAgents.tsx`, wording in `unavailableReasonText`), searched with the rest and opened while a search is typed. The bundled history is the raw registry, filtered by the same parser at load, so it needs no regeneration when the rules change. A removed agent's saved sessions, once stopped, show `RemovedAgentPanel` with **Add <Agent>**. `usePersistedState().saveNow` flushes state before a catalog action reads it and rejects when the write failed; writes run one at a time, and `AppStore::save_state` holds a lock around `state.json`.

**App updates.** `app_update.rs` holds `app_update_check`, `app_update_install` and `app_update_restart` (plain `#[tauri::command]` on `async fn`), built on `tauri-plugin-updater` used only from Rust (`UpdaterExt`), so the webview needs no `updater:*` permission (a test keeps it out of `capabilities/default.json`) and sends no URL. The endpoint (`latest.json` of this repository's latest release), the public key and `requireSignedVersion` are in `tauri.conf.json` `plugins.updater`: a download is installed only if its signature matches that key and records the version `latest.json` announces, and `is_allowed_download_url` (`ALLOWED_DOWNLOADS`) refuses a manifest whose package is not on `api.github.com` or `github.com` inside this repository (renaming it needs a release that accepts both names first, since installed copies carry the list; copies up to 0.7.0 only accept zorvo-releases, which is why `docs/development.md` has "The first release from this repository"). The client from `updater()` is https-only with connect, read and check timeouts, and `app_update_install` caps the download at 20 minutes. Both commands do nothing outside an app bundle (`runs_from_app_bundle`): under `pnpm tauri dev` or a bare `target/release/zorvo` the plugin would swap out the folder holding the executable, which is the cargo target; Tauri gives no executable path when a folder above it is a symlink, which also ends the check (logged on stderr). A check keeps the found `Update` in `PendingAppUpdate` (ignored while an install runs and after it); a manifest the download policy refuses counts as no update (`Ok(None)`), not as a failed check; failures of a check or an install are written to stderr, which only shows when Zorvo is started from a terminal (a Finder launch discards it). Install holds `PendingAppUpdate.install`, an async lock released on every path (a second call, from a page reloaded meanwhile, waits for the first and then finds the update installed), emits `app-update-progress` (`{phase: downloading|installing}`, `installing` before the signature is checked), installs and returns without restarting; calling it again after a success does nothing. The restart is its own command because `AppHandle::restart` ends the process without closing the page, so `pagehide` and `beforeunload` never fire: `useAppUpdate.install` calls install, then `beforeRestart` (`App.tsx`: `saveNow()` and the transcripts' `flush()`, which rejects when a write failed or a transcript is still loading, and then Zorvo stays open), then `app_update_restart`, which exits through `RunEvent::Exit` (workspace shells end; Zorvo never stops ACP agents on any exit). Frontend: `hooks/useAppUpdate.ts` (first check ~8 s after start, then daily, or after 15 minutes when a check could not be made; a failed check is silent, a failed install or save goes to `setNotice`; Later hides one version for this run; an answer arriving during an install is ignored), `components/AppUpdateNotice.tsx` (says what a restart ends: `busyCount` agents mid-turn and `terminalCount` live shells, worded by `restartWarning`), `lib/app-update.ts`; only the main window mounts `App`, so popouts never check. Releases are signed on the maintainer's Mac, never in GitHub: the Release workflow only builds (job `macos`, which runs the project's dependencies, so it holds no secret but the optional `APPLE_*` ones and publishes nothing) and keeps the DMG and the `.app.tar.gz` as the `release-build` artifact (30 days), under names made from the tag. The updater key, its password and any token that can publish releases are not GitHub secrets at all (a repository secret is readable by any workflow in the repository; the account's plan has no environments with reviewers, which was the first design). The build job gets a one-off key made on the runner, because `tauri build` refuses to run without one while `createUpdaterArtifacts` is on and `--no-sign` would also skip Apple code signing; the signature it makes is discarded. `node scripts/sign-release.mjs vX.Y.Z` does the rest (not a package script: `pnpm run` puts `node_modules/.bin` first on PATH), from a clean checkout of the tag. It proves HEAD, the tag on GitHub (`remoteTagCommit`) and the commit the newest successful run built are the same, reads the config and changelog once, downloads the artifact from that run with the maintainer's own `gh` login (`release-github.mjs`'s `downloadBuild`, which on a reset connection, timeout, EOF or 5xx tries again, 3 tries in all with a growing pause and an emptied directory, and says so on screen; any other failure ends it, and the last try's error is the one shown), checks it as data (`release-checks.mjs`: exactly the two expected files, a gzip package that holds only `Zorvo.app` with no hard links or links out of it, and an app binary that holds `tauri.conf.json`'s updater pubkey as text, a tripwire against a build that trusts another key, not a boundary), lists what changed since the last release tag in the dependencies, workflow and scripts and asks to go on, asks for the password hidden (never from the environment), signs with `tauri signer sign --app-version` using the CLI pinned in `scripts/updater-signer` (`signer-cli.mjs`: `npm ci --ignore-scripts` every time, run by `process.execPath`, kept equal to the root lockfile's version by `scripts/updater-signer.test.mjs`, so no project dependency runs next to the password), checks `latest.json` (`scripts/updater-manifest.mjs`: the six entries `tauri-action` wrote, with the package's asset API URL, which exists only after the upload) with `scripts/check-updater-signing.mjs manifest`, the package and the download policy before any write to GitHub, then makes or refills the draft release and uploads. The checkout is checked again before signing and before uploading. It passes the key's path to the CLI and never reads the file; the password goes only into the CLI's environment, and the project's folders and the key's variables are dropped from PATH and the environment of everything else. `--dry-run` writes nothing to GitHub. Not covered, said plainly in the README: a build compromised during a release that is then signed (the DMG too), and other code running as the maintainer on the Mac. `scripts/release-workflow.test.mjs` fails when a change gives the build job a secret other than `APPLE_*`, a token or a way to publish. The `macos` job still checks the tag against the three versions, and that CHANGELOG.md has a section for it, before it builds. `check-updater-signing.mjs key` checks a key with the pinned CLI. Never create, read or print the private key.

**Installer** (`src-tauri/src/installer/`). Zorvo installs an agent the user picks, plus Node.js or uv when it needs them, under the app data dir's `tools/`. Runtimes are pinned with their SHA-256 in `src-tauri/resources/runtimes.json` (`pnpm runtimes:update` regenerates it); every download is checked against a pinned hash, archives unpack with path and size checks, and each install is written to `tools/staging/` and renamed into place. Commands: `install_agent`, `install_runtime`, `cancel_agent_install`, `remove_agent_install`; progress goes out as `agent-install-progress`, and `agent-profiles-changed` follows every install. The plan is rebuilt in the backend from the agent id, never taken from the UI. **npm-package agents.** An agent the registry distributes as an npm package (`Distribution::Npx`) is never run through `npx`: its plan has a `PlannedStep::NpmAgent` step, which runs `npm install -g --prefix <staging>` like the Pi prerequisite and commits to `tools/agents/<id>/<version>/` with a record whose `bin` is the program to start (`installer/npm_bin.rs::choose_bin`, npx's own rule: the only program, else the one named like the package). `InstalledTools.agent_bins` holds those records, and `registry/resolve.rs::npm_agent_program` resolves the agent to that file, on the user's Node when it is new enough, else on Zorvo's first on `PATH`; no record, no `bin`, or a missing file reads as not installed. The entry's `version` names that dir, so `is_valid_entry` keeps an npx entry only when its version is one plain path name (a binary's must be an exact version; a uvx version is only shown). So starting an agent contacts no registry. `hooks/useAutoInstall.ts` (main window, after onboarding) installs the in-use agents the user has used (`usedAgentIds`: one with a session, the default agent, or one seen signed in; an agent only in use by default is not downloaded without a click) whose plan is exactly that one step (`autoInstallTargets`), one at a time through `startInstall`, because the install store shows only jobs the webview started. It reads the agents in use again each time it picks one and keeps only the ids it has tried, so an agent startup enables a render later still gets its turn, one taken out of use meanwhile is not installed, and each agent is tried once per run: a failure is not retried until the next start. uvx agents still run through `uvx`.

**ACP backend** (`src-tauri/src/acp/`): `jsonrpc.rs` framing, `connection.rs` one agent process (its `kill` ends the whole process tree through `background_processes::end_tree`, TERM then KILL after a grace period, since an agent may run its real process as a child, as Qwen Code's launcher does, and a stuck one ignores TERM), `manager.rs` maps app session ids onto ACP sessions. `reopen` (`acp/manager/reopen.rs`) continues a session with `session/resume` when the agent offers it, else with `session/load`. One agent process can host several ACP sessions (a native fork lives in its source's process), so connections are shared and killed only when their last session stops. Auth-required errors are surfaced to the UI as `ACP_AUTH_REQUIRED:` + JSON (parsed in `src/lib/acp-auth.ts`), both when a session opens and when a prompt is refused (Claude Code's adapter opens sessions signed out and refuses only the prompt).

**Session list and import.** `acp/session_list.rs` reads every page of the agent's `session/list` in one process (10 pages, 200 sessions), validates each `SessionInfo`, and ends the agent. The new-session draft offers what it lists through `useAgentSessionList` and `AgentSessionList`; `useSessionImport` records the session before `acp_import_session`, and `useAcpEngine.importSession` folds the load replay with `applyReplayUpdate`. The backend routes that replay through a notification-only `replaying` map, so a request during the import cannot deadlock; a resume-only import gets `historyElsewhere`, and the chat says the earlier messages stay in the agent.

**Models.** An agent may report its models in the session answer's `models` field (`{ currentModelId, availableModels: [{ modelId, name, description? }] }`, Gemini CLI does) instead of a model config option. `toModels` (`useAcpSessions.ts`) validates it into `AcpSessionInfo.models`, the probe returns it (`acp/probe.rs`, `useAgentProbe`) and `AgentOptions.models` remembers it. `acpControls` makes the composer's model chip from a `model` config option when there is one, else from `models`; Codex and Qwen Code report both, and for them the option carries every pick, so `changesToApply` ignores a `models` pick when `hasModelConfig` says the agent has an option (`models.currentModelId` only follows `setModel`, so after an option pick it is the model the session started with). A pick goes out as `acp_set_model` (`AcpManager::set_model`, the unstable `session/set_model` with `sessionId` and `modelId`; the spec's draft schema no longer documents it, Gemini still answers it); the UI sends only the ids. In a draft the pick is `AcpChoices.modelId`, remembered as `AgentOptions.preferredModelId` (`withPreferred`, while the agent still offers it) and applied by `changesToApply` as a `{ kind: 'model' }` change before the first prompt. A reopened session's answer may omit `models` (a `session/resume` answer does); then the remembered ones stay, the running session has no chip, and a pick is still sent as it is (`reopenedWith` in `changesToApply`), where the agent refuses a model it does not know. Gemini CLI's `session/load` does report them, but with `currentModelId` back at its default (`auto`, which can hang) whatever the session ran on, so a resume applies the remembered pick again before the first prompt (`startChoices` in `App.tsx`'s `resumeSession`). `FAKE_ACP_MODELS` makes the fake agent report models and answer `session/set_model`. `FAKE_ACP_USAGE` makes it send a `usage_update` with each prompt (30,000 more tokens of 200,000, 25 cents more) and offer `/compact`; `FAKE_ACP_CONTEXT_USAGE` makes it answer `qwen/status/session/context_usage` with the recorded answer.

**Composer controls from the agent.** `acpControls` (`lib/composer-controls.ts`) turns what the agent reports into chips. Modes, models and config choices keep their `description`; a mode whose id or name matches `RISKY_MODE` gets `risky`, which the open menu marks with a `ShieldAlert`. A model called "Default" with a short description shows as "Default (Opus)". Every `select` config option outside the categories `mode`, `model` and `thought_level` with at least two choices becomes an `ExtraControl` (Codex `collaboration_mode`, Claude `fast` and `agent`): a chip that sends `acp_set_config_option` like the effort chip and goes through `changesToApply` as a config pick. Only `model`, `thought_level` and `model_config` picks are remembered for the next session (`REMEMBERED_CATEGORIES`), so Plan or a persona never carries over. An agent reports the effort list of the model it runs only, so `AgentOptions.effortsByModel` keeps each model's `thought_level` option as reported (`withReported` for a session's report or a pick, `withEffortList` for a probe), and a draft on another model shows that model's list (`listsForModel` in `draftInfo` and `withPreferred`), or no effort chip while it is unknown, never the reported model's; a pick its list lacks is not shown, and `withPreferred` keeps a remembered effort for a model whose list is unknown, since `changesToApply` checks it against the agent's list once the model is set. A list over 10 choices gets a search field. `SAFE_MODE_IDS` puts `workspace-write` before `read-only`; Codex's default `agent` ("Auto review") is deliberately not risky (pinned in `acp-modes.test.ts`).

**Probing a draft's agent.** ACP agents report modes/models/efforts/slash commands only inside a session, so `acp/probe.rs` (`acp_probe_agent`) asks in a short-lived process. Opening a session can run the user's session hooks and lands in the agent's history, so it opens one only to learn a never-run agent's options or to check the sign-in of an agent that cannot report it, and deletes it in the background (`session/delete`, else `session/close`). An agent that pushes `_auth/status_update` (Claude Code) and whose options are known is only asked who is signed in. `signInChecked` in the result says whether the sign-in was actually seen. Opening a session proves nothing for an agent that cannot report its sign-in and refuses only the prompt (GLM Agent), so for an agent without `_meta.authStatus` the probe also checks the variables its `env_var` methods name (`missing_key_variables` in `acp/key_env.rs`): a variable counts as set when it is non-empty in the launch environment or in Zorvo's own; only presence is read, never the value. An agent that also offers a `terminal` method, or one `env_var` method with all its required variables set, is left alone. Otherwise `signInChecked` is false and the answer's `missingEnv` holds the names (`useAgentProbe` keeps only valid variable names); Check sign-in and the draft check then drop a recorded Ready (`markUnconfirmed`), so the chip reads Not checked, not Sign in, and Settings' row says which variable to set (`unconfirmedMessage`). `src/hooks/useDraftAgentCheck.ts` drives it for a new-session draft (via `useAgentProbe`), keeps the sign-in panel in step and asks again on window focus while a sign-in is pending; results are merged with `withProbed` (`lib/acp-draft.ts`), which never overwrites what a real session reported.

**Terminal sign-in.** Zorvo advertises `auth.terminal`. `acp_start_terminal_sign_in` reads a `type: "terminal"` method from a fresh `initialize` (`acp/terminal_auth.rs`, same env deny list as the registry) and runs the agent's own program plus the method's args in a PTY with a `signin-` id. Its output goes on `sign-in-terminal`. `useAgentSignIn` re-checks with the probe and sends the refused message through `retryAfterSignIn`. `authenticate` is never sent for a terminal method. **Agent setup:** a method in the older form, with no `type` and `_meta.type: "terminal"` (Qwen Code's only one: `openai`, `_meta.args: ["--auth-type=openai"]`), marks the agent's own interactive setup, where it picks its provider. `acp_start_agent_setup(profileId, cwd, terminalId)` (`acp/commands.rs`) runs it only when a fresh `initialize` reports one (`has_interactive_setup`, `AcpManager::agent_setup_with` in `acp/terminal_auth.rs`). It runs the agent's own program from the registry without the entry's own arguments (`AgentProfile.setup_args`, filled in `registry/resolve.rs`) and without the method's `args`, in the sign-in PTY under a `signin-` id. The UI sends no method, command or argument.

**Which agents are ready.** An agent counts as signed in only when it was seen so: `useAgentSignInStatus` (memory for `needed`, `settings.signedInAgents` for the rest, which the backend `Settings` also keeps) is told by `useDraftAgentCheck` when a probe shows someone signed in, by `useAgentSignIn` when a sign-in or **Check again** takes, and when an agent asks for a sign-in (`requestSignIn`). The sidebar chip (`lib/agent-sign-in.ts`) reads Ready, Sign in or Not checked; Zorvo never asks every agent at startup, since a probe can open a session in the agent. ACP gives `-32000` the meaning "authentication required" but fixes no message, and the spec has no way to ask whether anyone is signed in. So a refusal counts as a sign-in request (`is_auth_required` in `acp/manager.rs`) when it is `-32000` and either its message has a word in `SIGN_IN_WORDS` (including "API key" and "credential", as Gemini CLI words it), or the agent offered sign-in methods in `initialize` and the refusal answers `session/new`, `session/load`, `session/resume` or a prompt; `session/list` needs the wording. A `-32000` from an agent with no methods stays a plain error. A `-32603` ("Internal error") counts too, but only when the agent offered methods, the refusal answers one of those requests, and its `message`, a text `data`, `data.details` or `data.message` has a whole sign-in word or two-word phrase (`mentions_sign_in_phrase`: `SIGN_IN_WHOLE_WORDS` such as "unauthorized" or "apikey", `SIGN_IN_PHRASES` such as "log in" or "API key"; letters inside another word, as in "designing" or "catalog in", do not count, unlike the looser letters-only `SIGN_IN_WORDS` check of `-32000`) (GLM Agent opens sessions without a key and fails the first prompt with `-32603` and "No API key found" in `data.details`); any other `-32603` stays a plain error. The rule lives in `acp/manager/sign_in.rs`, with its unit tests, and `FAKE_ACP_PROMPT_ERROR_DETAILS` makes the fake agent refuse prompts that way. Methods Zorvo cannot run (`explain` in `lib/acp-auth.ts`: keys, Vertex AI, gateway) get text, never a button, and the panel's **Check again** (`auth.recheck`) re-asks through `checkSignIn`, after `refreshLoginEnv` (`lib/sign-in-check.ts`: the `refresh_login_env` command, which only calls `env_resolver::refresh_user_env()` and returns nothing; `launch_for` only ever reads the cached environment, so without it a key exported in `~/.zshrc` after start is never seen; it is not `get_agent_profiles(refresh: true)`, which also refetches the registry and runs `npm`). **GitHub connection.** Zorvo reads and sets up the user's GitHub sign-in only through their own `gh`, for github.com only, and holds no token. `github_status` (`github.rs`) runs `gh auth status --hostname github.com --json hosts` (its JSON names the login, the state and `tokenSource`, and gh adds the token only for `--show-token` / `-t`; never pass either, and never run `gh auth token`; a test pins every argument list) and, when signed in, `gh api user --jq '{login: .login, name: .name}'`, so only the login and the display name ever reach Zorvo, and neither is stored. `parse_auth_status` is the pure part, with fixtures taken from real `gh` output: the active account wins when there are several; an account whose stored token GitHub answered 401 reads as signed out, but a 401 for a token from `GH_TOKEN` or `GITHUB_TOKEN` (`tokenSource`) reads as `unknown` with `canConnect: false` and a message naming the variable, since `gh auth login` refuses to run while it is set; one that could not be tried (no network, a timeout, an old `gh` without `--json`) is `unknown` too, and JSON of any other shape is an error, hence `unknown`: only a `hosts` object without github.com, or an empty list, means signed out. Logins may hold `_` (Enterprise Managed Users). The result is `{state: not-installed | signed-out | signed-in | unknown, login, name, message, canConnect}`. The runs go through `pull_requests::capture_gh` (the login-shell environment minus `CLICOLOR_FORCE`, `GH_FORCE_TTY`, `GH_REPO`, `GH_DEBUG` and `DEBUG`, with `NO_COLOR=1`, 20 s timeout, prompts off; the pull-request commands run the same way, so they honour the shell's `GH_TOKEN`, `GITHUB_TOKEN`, `GH_CONFIG_DIR` and proxy settings). `github_start_sign_in` runs the fixed `gh auth login --hostname github.com --web` in a PTY (a test pins the arguments; no `--git-protocol`, which gh applies to the whole host, so gh asks in the terminal and the dialog says so) under a `ghlogin-` id, which `pty_event_route` sends to the `github-sign-in-terminal` event, so it never meets an agent's `signin-` terminals; input, resize and cancel reuse `send_input`, `resize_session` and `terminate_session`. Frontend: `hooks/useGithubConnection.ts` (status read at start, on **Check again**, when the sign-in terminal exits with any code or its dialog closes, and on window focus while not connected, never while a check is still running; owns the sign-in terminal, shown in `TerminalSignInDialog`, and `SettingsPage` moves focus to the section when that dialog closes after a sign-in that worked), `components/settings/GithubSection.tsx` (Settings → GitHub: not installed with `brew install gh` and a link to cli.github.com, signed out with **Connect**, signed in, unknown), `lib/github.ts`. The sidebar footer shows GitHub name → `@login` → git name → git email → "Local user" with a GitHub mark while signed in (`ProfileFooter`); initials stay initials, since an avatar would be a download. When the Changes panel cannot list pull requests because `gh` is missing or signed out, in a repository with a github.com remote (`WorkspaceDetails.hasGithubRemote`, read from the repository's `config` file by `git_info.rs`, no git run), it says so and opens that Settings section instead of showing gh's raw error. Not built: sign out, switching accounts, avatars, enterprise hosts, installing `gh`.

**Artifacts.** An agent shows the user a web page it wrote, beside the chat (design in `docs/superpowers/specs/2026-11-16-artifacts-design.md`, with both spikes' results; artboards beside it). Dropping a `wry::WebView` does not end its page (wry keeps the `WKWebView` alive, and a looping page then holds a core until Zorvo quits), so `view::end` first sends the `WKWebView` `_killWebContentProcess`, guarded by `respondsToSelector`; every close goes through it. The start-up sweep is skipped when the state lists no session (`sessions_to_keep`): a corrupt `state.json` is read as an empty state. `wry` is a direct dependency pinned to Tauri's version (a test keeps one `wry` in `Cargo.lock`). The `zorvo-artifact://localhost/<session>/<artifact>/<version>` protocol exists only on that webview; `PAGE_CSP` (a test pins its text) allows inline script and the CDNs Claude's artifacts use, nothing in `connect-src`, and ends in `sandbox allow-scripts`, which gives the top-level page an opaque origin (without it two artifacts shared `localStorage`). Its navigation handler allows only artifact pages and is the only barrier to the open web. Every `artifact_view_*` call goes through one module-level queue, so calls never overtake each other; the page is asked for only once its box has a size. The one view is shared by every box: `claimed` (the page a mounted box wants) and `live` (the page the backend's view holds) are module state, a box that leaves only gives up its claim, and the close goes out only if nothing claimed the page by its turn in the queue. So Expand and Shrink, which swap one viewer for another in one commit, move the same view (`artifact_view_bounds`) and the page keeps what was typed or scrolled in it; Reload and another version make a new view. The child is a native layer above the HTML, so `useBoxCovered` hides it (`artifact_view_hide`) whenever something is on top of the box at a grid of points, or the box has no size (Settings and the gallery hide the main section rather than unmount it); a zero rectangle is never sent as bounds, and bounds wholly outside the window keep the view but stop drawing it (`Display.is_outside`). It is the agent's own report: `action` says what a tool was for, and a row claims it (`statusWord`) only at `completed`, since an agent can send a diff before a permission is refused; a kept `running` tool reads Did not finish once the session is idle. `ToolExecution.command` comes from `rawInput` (`commandOf`), and an empty update never unnames a tool's files. Only file changes are checked: `unreportedFiles` lists files in git's stats (since `startCommit`, else HEAD) that no `completed` `changed` or `touched` entry names, matching under `cwd` and then under the canonical `root`, because reading a file does not report changing it. Commands, prompts and paths go through `escapeVisible` (`lib/visible-text.ts`) as text, never markdown. `activityOf` caches per message in a `WeakMap`, since updates flush per frame.

**File viewer.** The Files tab (`components/FilesPanel.tsx`) marks changed files and their folders (`lib/file-markers.ts`, from `useInspector`'s HEAD stats with `filesPrefix`, since stats name repository paths), and a click opens `components/files/FileViewer.tsx` in the tree's place (`useInspector.viewedFile`; another folder closes it; the inspector widens like the Terminal tab). Not available, because the CSP has no `'wasm-unsafe-eval'` and the cmaps and standard fonts are not bundled: JPEG 2000 and JBIG2 images, some ICC colour profiles, and non-embedded CJK fonts. **Agent tools.** Groundwork for Zorvo's own MCP server, so an agent can call tools such as `delegate` (`src-tauri/src/agent_tools/`; design in `docs/superpowers/specs/2026-11-13-zorvo-mcp-tools-design.md`). The nine tools work: `list_agents`, `delegate`, `start_session`, `read_session`, `stop_session`, and `show_artifact` and `artifact_guide` (see **Artifacts**), plus `browser` and `browser_guide` (see **Browser**). **Bridge:** the executable has a second mode, `zorvo mcp-bridge` (`bridge.rs`, checked in `main.rs` before Tauri starts, so no window opens). An agent starts it as a stdio MCP server; it reads `ZORVO_MCP_SOCKET` and `ZORVO_MCP_TOKEN`, sends the token as a first line and then only copies bytes both ways (the MCP is spoken by the backend). It prints at most one plain line on stderr and never the token. **Socket** (`socket.rs`): `<data dir>/agent-tools/s.sock`, or a short `/tmp/zorvo-<uid>-<hash>/s.sock` when that path would not fit in a socket address (100 bytes); the directory is 0700 and owned by the user (checked), the socket 0600, a socket left by a dead run is replaced after a failed connect and a live one is never taken over, and dropping the listener removes the file. A connection must send a known token within 2 s (first line at most 4 KiB), otherwise it is closed. **Tokens:** one random 32-byte hex token per app session (`Tokens::issue(session, Capabilities)`, compared in constant time against every stored token), in memory only, never logged or written; `forget` ends it with the session. A token carries what its session gets (`Capabilities { agent_tools, computer_use, path }`, from `tools_for_session` / `servers_for_session`, which read `Settings.agent_tools` and the strict-off `Settings.computer_use`); `handle_line(line, &Caller)` lists and accepts only those tools, so a session with computer use alone still gets the `zorvo` server but not `delegate`. **Peer check:** a token is accepted only from the session's agent process or a descendant (`agent_tools/peer.rs`: the peer's pid from `LOCAL_PEERPID`, parent walk with `proc_pidinfo`, pid and start time compared at every step, at most 64 steps), since any process of the same user can read another's environment. `AcpManager::set_process_listener` reports each session's agent pid right after the process starts (before `initialize`, so a bridge started during `session/new` already passes), and a native fork gets its source's; `lib.rs` binds it with `AgentTools::bind_process`. A session with no bound process accepts no connection. **MCP subset** (`protocol.rs`, pure `handle_line`): `initialize` answers with the client's `protocolVersion` when it is in `SUPPORTED_VERSIONS` (`2025-11-25`, `2025-06-18`, `2025-03-26`, `2024-11-05`), else the newest; `ping`, `tools/list` and `tools/call` work, and `tools/call` serves the five tools in `tools.rs` (`list_agents`, `delegate`, `start_session`, `read_session`, `stop_session`; `validate` checks arguments and caps text and titles; bad arguments are a tool result with `isError`, an unknown tool is `-32602`). Every other method that carries an id (`prompts/list`, `resources/list`, `server/discover`, which Qwen Code and Claude Code send) gets JSON-RPC `-32601`, never a dropped connection; a notification gets no reply; batches and lines over 1 MiB are refused. **Calls** (`service.rs`, `AgentTools`): a `tools/call` is parked in a pending table and emitted as the Tauri event `agent-tool-call` (`{callId, sessionId, tool, args}`); the webview answers with `agent_tool_respond(callId, ok, text)` (`agent_tools/commands.rs`), and the text goes back on the agent's connection as the call's result (`isError` when `ok` is false). A call ends with an answer, after `CALL_TIMEOUT` (170 s, since Antigravity gives up on a tool call at 180 s and Qwen Code and Codex at 5 minutes; the agent is told Zorvo did not answer in time), when the agent sends `notifications/cancelled` whose `requestId` equals the call's JSON-RPC id on that connection, or when its session is forgotten or the app exits; each end that is not an answer emits `agent-tool-call-ended` (`{callId}`), and a later `respond` for it does nothing. `AgentTools::start` takes the `emit` and `ended` callbacks (`start_with_timeout` is for tests); `AgentTools::disabled()` has no socket, is used when binding fails and by tests that open no tools, and always returns `[]`. **Handing a session its server:** `servers_for(sessionId, enabled)` issues the token and returns the ACP `mcpServers` entry (`{name: "zorvo", command: <this executable>, args: ["mcp-bridge"], env: [{name, value}]}`), or `[]` when not enabled. `acp_start_session`, `acp_reopen_session`, `acp_import_session` and `acp_fork_session` take `agentTools: bool`; `servers_for_session` reads `Settings.agent_tools` only when the webview asked, so both must be true, and `forget_if_failed` drops the token when the session did not open. `Settings.agent_tools` is described under **Setting** below. The webview's flag is `sessionGetsAgentTools` (`lib/agent-tools.ts`: false for a compare-run session or a delegated one, true for a plain session and a fork), passed by `useAcpEngine`. **Webview:** `hooks/useAgentTools.ts`, mounted by `App` (main window only; a popout would answer twice), answers every `agent-tool-call`, on every path, since an unanswered call costs the agent its own timeout. `lib/agent-tools.ts` holds the pure rules: `parseToolCall`, `resolveAgent` (an exact id, else exactly one agent whose name matches but for case; part of a name never matches, and the error lists the ids), `statusRefusal` (not installed, needs a sign-in), `listAgentsText` and `delegateResultText` (the JSON an agent reads), and the fixed answers `DECLINED`, `NO_SESSION`, `NO_SUCH_HANDLE` and `UNREADABLE`. `list_agents` is answered at once with the agents in use and this session's delegates; the hook is given `agentsInUse`, not every detected profile, so an agent the user took out of use is neither listed nor reachable by `delegate`. `delegate` resolves the agent and then needs a **grant**: memory only, per session, gone after a reload, taken back from the ⋯ menu (**Stop allowing delegation**; `revokeGrant` also declines the allowed calls that still wait their turn, while one that already runs finishes). Without one the call waits and the session's chat gets a card Zorvo makes itself (`lib/agent-tool-card.ts`, `ActionCard.zorvoTool`; never the agent's own permission request, since Qwen Code and Codex ask none for an MCP tool): the caller, the target, the folder and the task as text with its line breaks kept and every other control or bidi character spelled out, with **Allow for this session** and **Deny**. Several calls that wait in one session share one card that lists every task, each line of a task marked `> ` so a line the agent wrote cannot read as another request's heading. Allow records the grant and runs the waiting calls in arrival order through `useDelegation.giveTask(…, { byAgent: true })`; Deny answers each "The user declined." and keeps no grant. `agent-tool-call-ended` (the backend's timeout, the agent's cancel, a stopped session) takes that call off the card, and a card with no call left reads Not answered; a card loaded from a transcript is never pending (`loadTranscript` settles every pending card). The card's answer is routed in `App.tsx`'s `chooseOption` (`agentTools.chooseCard` first, else the engine's `acp_respond_permission`), which a popout's `choose-option` also goes through, and a session with a pending Zorvo card counts as waiting (`isSessionWaiting`). A compare-run session, a delegated one, one an agent opened, an unknown one, or one whose agent has exited (`status: terminated`; the backend also forgets its token on `AcpEvent::Exited`, in `lib.rs`'s event sink, so a process the agent left behind cannot speak for it) is told it cannot use the tools. **Sessions an agent opens (`start_session`).** An independent session is an ordinary session with `Session.openedBy` (`{ sessionId, at }`, kept leniently in `persistence.ts` and `store.rs`, `STATE_VERSION` stays 2): the brief is its first message with no hidden context, it sends no report, it is not selected, and `sessionGetsAgentTools(session, sessions)` is false for it, so it cannot open more (one level), and for any fork of a session that has no tools (it walks `forkedFrom`; a source that is gone cannot be judged, so such a fork has them). The rules are pure, in `lib/agent-tools.ts`: `resolveFolder` takes only a path that is, character for character after one trailing slash, a folder in Zorvo's list and not the caller's own (`ownFolderOf`: its repository when it works in a worktree); nothing is normalised or resolved there, the error lists the other folders' names and never repeats what was asked, and `acp_start_session`'s `ensure_known_workspace` checks again. `otherFolders` is what `list_agents` returns as `folders`, next to `opened` (`openedSessionsOf`); `sessionTitleOf` is the agent's title or the agent and the brief's first line; `openRefusal` holds the limit, `MAX_RUNNING_OPENED` (3) of an opener's sessions in a turn at once. `hooks/useOpenedSessions.ts` opens it through the app's own `startSession` (`focus: false`) and, for `worktree: true`, `createSessionWorktree` from the opener's repository (the agent names no branch or path); in its own folder the new session shares the opener's worktree. Places are counted in a ref (`underWay`) from before anything awaits until the session is listed, so four calls in one tick open three. A request that ended while git made the worktree (the caller was stopped or deleted, the call timed out or was cancelled) starts nothing: `useAgentTools` keeps every allowed call that has not finished in `approved` (running, or queued behind another of its card), marks one whose `agent-tool-call-ended` arrives, skips a marked call that has not started, and `open` reads the mark through `OpenRequest.isCancelled` after the await, removes the unused worktree and frees the place. A worktree that cannot be made, or a `startSession` that throws, opens nothing, frees its place, and returns a reason written for the caller with the error in `detail`, which `useAgentTools` shows the user as a notice and never sends to the agent. `startSession` itself does not wait for the agent: the tool answers `opened` once the session is recorded, so an agent that then fails to start (not signed in, say) leaves a session with the brief back in its composer while the caller was told it opened. In `useAgentTools`, a `start_session` in the caller's own folder joins the same queue as `delegate` (`enqueue`): it runs under the session's grant, or waits on the session's card, which lists every waiting request under its own heading (`toolCardFor`: "For {Agent}:", "New {Agent} session:"). A `start_session` with `folder` never uses the grant: each gets a card of its own (`folderCard`, kept in `folderCards` by card id) with **Allow once** (`ALLOW_ONCE`) and **Deny**, shown even when the session has a grant, and Allow once records none. So one session can show a grant card and folder cards at once, each answered on its own. **Delegation.** A session (A) hands a task to another agent's session (B) and gets B's answer back. Three ways in, one path: the top bar's ⋯ menu (`DelegateDialog`, `useDelegateDialog`), an `@Agent task` mention at the start of the composer (`delegationMentionOf`, `mentionBlockedReason`), and the agent itself through the `delegate` tool (see **Agent tools**); all end in `useDelegation.giveTask`. The link is `Session.delegatedFrom` on B (`DelegationLink`; an open link has no `endedAt`), so nothing else is stored. **One open delegate per agent:** `openDelegatesOf(A)` lists A's (oldest first), `openDelegateOf(A, agentId)` finds one agent's, `sourceOf` finds A even when archived, and a delegated session can never delegate (one level). `lib/delegation.ts` is pure. `taskRoute` decides where a task for an agent goes: `start` (no open delegate of that agent), `follow-up` (its delegate is idle: the task is that session's next prompt), or `blocked` (a private source, since a delegate is an ordinary session of another agent and the handoff would leave the TEE unasked; the delegate works or waits for an answer: "… is still working on the previous task."; a delegated source; a source with no messages, with the empty reason; a busy source, unless its own agent asks, `isSourceBusyAllowed`). `delegateBlockedReason` is the route's reason (source-only checks when no agent is named, as for the menu item). `sendBlockedReason` blocks only B, while A works on B's report; A's Send is never blocked by a delegate, since A may hold several and the user steers it. `buildDelegatePrompt` is one line of hidden context naming the handoff file, `reportMessage` quotes B's last complete answer with `> ` (a whole reply with no text, tool calls only, is reported as finished without a written answer), cut at `MAX_REPORT_CHARS` (20,000), with the files B reported changing, all through `escapeVisible`, and `followUpSummary` is the composer's line for a mention that goes to an existing delegate. `hooks/useDelegation.ts` does the effects. `giveTask(sourceId, agentId, task, { byAgent })` returns what happened (`started`, `sent`, or a reason) and never raises a notice; `start` wraps it for the dialog and the mention and turns a refusal into a notice. A start writes A's conversation as a fork-style handoff (`write_fork_handoff`) and starts B in A's folder and worktree with the task as its first message; with `byAgent` the handoff stops before A's unfinished reply (the one that holds the tool call), B is started with `focus: false` and is not selected. Guards keep the route honest between renders: a further task holds its delegate in `sendingTo` from before the send until the delegate is seen busy or its turn ends, so two tasks for one idle delegate in the same tick do not reach the same turn (busy is React state and is not observable in that tick); and three more: a start is held in `starting` (by source and agent) from before the handoff is written until the new session is listed, so a second task for the same agent in the same tick is refused, not started twice; a follow-up is refused while that delegate's last report has not reached A (`isHandingOver`), since the task would become B's last message and the waiting answer would be lost; and a delegate whose session is `terminated` gets its link ended and the task starts a new one. A failure inside Zorvo comes back as `isInternal` with the error in `detail` for the user's notice, and an agent is told only "Zorvo could not do that." A follow-up is sent with `send(B, task, …, { delegationTask })` (the message reads **Task from {A's agent}** in B's chat, `MessageRow`) and B's link takes the new task, which the next report quotes. **Reports wait their turn:** `onTurnEnded` (fed by the engine's turn ends) puts B's finished turn in `pending`; the drain sends a report only when A is neither in a turn nor waiting on the user, at most one per source per pass (taking it starts A's next turn), oldest first, as a user message marked `delegationReport`. It is given back into A's composer, with a notice, only when A is idle and still cannot be prompted (not running, agent removed, sign-in needed) or when the agent refuses it. B's Send is blocked while its report is queued ("…'s report waits for … to finish.") or being sent (`delivering`). Same-tick decisions read refs, outcomes are memory only, and `end` closes the link and drops a queued report. `viewsFor` gives a source one status line per open delegate (`DelegationStatusLine`, oldest first) and a delegate its own (`DelegatedFromLine`); the Delegate dialog shows where the task goes in place of the model, effort and mode chips for an agent that already has a delegate (`DelegateAgentChoice.hasDelegate`; an existing session keeps what it runs on, so no pick is sent), the ⋯ menu lists **End delegation to {Agent}** per delegate when there are several, and archiving A ends them all. Not built: a delegate in another folder or its own worktree, nested delegation.

A run that goes away while its panel is open, with one listed session left, selects that session (`lastOfRun`) in the same render, in `App.tsx`, so no draft mounts; with another session on screen the selection stays. **Sign-in.** A run's refusal never takes the `authRequest` slot when it arrives: `App.tsx` sees `isInRun` and calls `keepSignIn`, so several refusals at once cannot fight over one slot and no panel covers the run. It is kept in memory on the row (`signInNeeded`, which reads Needs sign-in) until the row is opened, and only then does `takeSignIn` ask through `signIn.handBackKept`, since only then does its composer show. `dropSignIn` ends it once the message goes out or the user changes it; memory only, so after a restart the row reads Stopped. `watchedRuns` holds the runs started in this window, the only ones that notify, once, when they settle; `awaitsRunNotice` holds back each session's own notice meanwhile.

**Artifact comments.** The user marks text or an element on an artifact page and writes a comment for the agent (design in `docs/superpowers/specs/2026-11-17-artifact-comments-design.md`, artboards beside it). **Page side:** the child webview gets one initialization script, `src-tauri/src/artifacts/page_script.js` (a test pins its SHA-256, so a change is a visible one; `src/test/artifact-page-script.test.ts` runs it in jsdom), and one wry IPC handler. The script defines `__zorvoCommentMode(on)` and `__zorvoMarks(marks)` (not writable), catches clicks in the capture phase while comment mode is on, reports `pick-element` (tag, id, five classes, label, text, an `nth-of-type` path of at most 12 levels), `pick-text` (cut from the concatenated text nodes by the selection's offsets, never from `Selection.toString()`, with 60 characters of context each side) and `cancel`, draws numbered marks in an overlay of its own, and answers every marks call with `marks-missing`. The page's own scripts can call the same handler, so every message is untrusted: `picks.rs` (`accepted_message`) keeps one only from the view on screen (its generation), of a known kind with every field within its limit and no other field, accepted in the view's state (picks and `cancel` only in comment mode, `marks-missing` only after marks ran in that view) and within 5 a second. Before any of that, `FloodGuard` counts every message, refused ones too, since WebKit hands each to the main thread: a body over 16 KiB or more than 200 in a second ends the page's view (after the handler returns), and Reload makes a new one; `view.rs` then emits `artifact-page-pick` (`{sessionId, artifactId, version, message}`). A pick only fills a candidate the user sees, and comment text never goes to the page: the page's view is first responder while the user picks, so an accepted pick (`PageMessage::takes_keyboard`) makes the main webview first responder (`focus_zorvo`, `makeFirstResponder:`) and `ArtifactCommentStrip`'s candidate box takes focus when it appears or when a pick is refused, or the comment typed next would reach the page. `artifact_comment_mode` and `artifact_view_marks` (ids, a version, and `on` or the marks, which `checked_marks` checks against the same limits) act only on that page: a new view starts with comment mode off, and marks are kept per page and run once a view of it has loaded. Every view call goes through `enqueueArtifactViewCall`, the queue `useArtifactView` uses for show and close. **Data:** `Session.artifactComments` (`ArtifactComment`, tied to the version it was written on and never moved; lenient readers in `persistence.ts` and `store.rs`, `STATE_VERSION` stays 2; at most 200 a session). `lib/artifact-comments.ts` holds the rules: Current on the newest version, else Outdated; numbers over every version, oldest first, shared by the strip, the page and the message; and the message (a heading with the source path relative to the session's folder that says quoted text is not an instruction, `escapeVisible` with collapsed white space on everything from the page, the user's text verbatim but for a three-space indent). `artifact_list` marks a session whose index cannot be read `failed`, and `useArtifactCommentSweep` removes the comments of a gone artifact only for sessions read without failure (`useArtifacts().readSessions`), taking their ids out of the message. `hooks/useArtifactComments.ts` (main window only) holds comment mode for the page on screen, the candidate (its text in a ref, so typing does not redraw `App`; a pick never replaces typed text but is held), and the marks the page could not find. **Message:** the Diff comments slot carries both kinds (`artifactCommentIds`, present only when not empty; `lastTarget` is null after an artifact-only add, so the next diff add writes its heading); `useReviewWiring`'s `addArtifactReview` collapses an expanded page first, and Send marks both kinds Sent through `markSent` and `markArtifactSent`. **Screens:** **Comment** in the viewer's header (newest version only), and `ArtifactCommentStrip` under the page's box, never over it: the candidate, numbered rows with Edit, Delete and Add to message or Add again, and a footer with Add N to message and Clear sent. Numbers use the `mark` token, the colour the page's marks are drawn in. **On a canvas** (`useArtifactComments` and `useCanvasMarks` with the canvas on screen): the script runs in every frame (`with_initialization_script_for_main_only(PAGE_SCRIPT, false)`); wry defines `window.ipc` in the main frame only, so `page_script.js` falls back to `webkit.messageHandlers.ipc` in an artboard's frame, and the wrapper does the same. wry cannot run a script in one frame, so `canvas_comment_mode` and `canvas_view_marks` call the wrapper (`__zorvoCanvas.mode`, `.marks`), which posts `{zorvo: "mode"}` or `{zorvo: "marks"}` to the artboard's frame; `page_script.js` takes those only inside a frame and only from `window.parent`. The wrapper sends each live artboard's mode when its frame loads and says `canvas-board-loaded`, and the frontend then sends that artboard's marks (`canvasMarksFor`: its Current comments on text or an element). The selected artboard's **Comment** writes a comment on the whole artboard (anchor `{kind: "artboard"}`, no mark). A canvas comment is an `ArtifactComment` whose `artifactId` is the canvas key, `version` is 0 and `canvas` is `{key, artboardId, fileHash}`, the SHA-256 of the artboard's file read when the pick arrived (`CanvasCommentRecord` in `store.rs`, lenient like the rest); it reads Current while the file has that hash and Outdated otherwise, a gone file included (`canvasCommentStatus`), and never moves. Numbers run over the whole canvas. The sweep of gone artifacts leaves canvas comments alone. The message (`canvasMessage`) is grouped by artboard in canvas order under "Comments on `design/checkout/pay-b.html` (Checkout, artboard Payment B)", the file relative to the session's folder (`canvasHeading`), with the quote rules above.

**Diff comments.** The user comments on lines in `DiffView` (the full review, which opens in the chat's place from the top bar's diff chip or the Changes tab; Shrink, or Add to message, brings it beside the chat so the composer shows) or in the inspector's Changes tab, adds them to the composer, reads or edits the text, and presses Send: there is no other way out for a comment. A comment belongs to one session (`Session.reviewComments`, `store.rs`'s lenient per-item reader, `lib/persistence.ts`; `STATE_VERSION` stays 2) and is checked only against the diff it was written on: its `target`, `side` and `line`, by `commentStatus` (`lib/review-comments.ts`). The row at that line with the same `lineHash` is Current; a row that differs or is gone, or a file the target no longer lists, is Outdated; a diff cut before or on that line, or a failed read, is Unknown; another target is Not in this diff. Add N counts Current and Unknown comments that are neither In message nor Sent; an Outdated one has its own Add, and its text says the line is gone. A comment never moves: about a third of this repository's non-blank lines repeat within their file, so searching for the text would attach a comment to the wrong line and the message would confirm it. `lib/review-comments.ts` also words the message; quotes and paths have control characters, U+2028, U+2029 and bidi controls turned into visible escapes, so the user reads what the agent reads, and the body stays verbatim. `session_diff_targets` gives the root and the folder's prefix, so paths are relative to the agent's folder and a file outside it gets its absolute path. `session_file_diff` takes `since` for `DiffTargetId` `'start'` (**Start of this worktree**), offered with `worktree.startCommit` and the default only for a session with a `compareRunId`; a compare row's numbers open it (`onReview`). The controls are opt-in through `FileDiff`'s `review` prop, which `DiffView` and `ChangesPanel` pass for a session on screen, both through `hooks/useFileReviews.ts` (the file reads, the statuses, the `CommentAdder` and each file's `FileReview`), so drafts have none. The Changes tab lists what Commit would take, so its comments are always on `head`, and its bar lists only those; a comment on another target stays the full review's, which can show that target. `hooks/useReviewComments.ts` holds the session's comments and the boxes being written. `hooks/useReviewMessage.ts` holds one slot, `{ sessionId, commentIds, artifactCommentIds?, lastTarget }` (artifact comments share it, see **Artifact comments**), since one `ComposerDock` serves every session and keeps its text across a switch, so Zorvo must remember whom added comments are for. The slot is in memory only because composer text is too: after a restart an In message comment is a plain comment. It lifts when the composer is emptied or `ComposerHandle.restore` replaces the text (a rewind, or a worktree or run that failed to start), since the comments go with it. `ComposerHandle.giveBack` keeps the composer's text, so it never lifts a slot. Text with comments that comes back keeps its owner: `lastSends` keeps, per session, the text and target of its last send that held comments, by session since one message may wait while another session sends, and drops an entry when its text arrives or its session goes away. `restore` of exactly that text re-arms the slot for that session with no comment ids. `giveBack` does the same through `onGivenBack`, which gets the returned text, not the text it joined, when that holds the message as a whole block, since `useUnsentMessages` joins several; a slot already set for the session keeps its comment ids. While a slot belongs to another session, nothing is given back to this one (`isHeldFor`): `useUnsentMessages` keeps the message and delivers it on the render after the slot lifts, and `useAgentSignIn` routes its direct calls through the same gate, so a held refusal opens no `pending` and is not resent on its own after the sign-in. Otherwise A's text would join B's comments, whose note points to B, and go to B's agent. Send from a re-armed slot marks nothing new. While the slot is set and the composer holds text, Send is blocked everywhere but the slot's session, which `hooks/useReviewWiring.ts` also blocks when it cannot continue, since Send would otherwise start a new session (`reviewOwner`, `composerNote`; the note names a compare run's session by its agent, as all of a run's sessions share one title). A compare run's panel hides the composer and does not unmount it (`hidden` in `App.tsx`), so a look at the panel keeps the message; `insertPaths` drops what comes in meanwhile, so nothing goes into a message nobody can see, and the restores wait for the composer to show. `RemovedAgentPanel` shows in the composer's place the same way (`isComposerHidden`), so a look at a removed agent's session keeps the message too. A hidden composer takes nothing: a message that comes back to a removed agent's session, whatever the session's status, waits (`isMessageHeldFor`, which `useAgentSignIn` also reads before it resends), and a rewound one waits in `pendingRestoreRef` under its session id, until Add brings the composer back. Zorvo marks Sent rather than guessing what reached the agent: `acp_prompt` returns on write, stop reasons differ per agent, and matching text in an editable box breaks on one typo. So `sentAt` says Send was pressed, not that the agent acted; a Sent comment stays with **Add again**, keeps its status so a line the agent fixed reads Outdated, and **Clear sent** removes them. Editing an In message or Sent comment makes it plain, and the text already in the composer or the chat stays.

**Computer use (looking only; acting is not built).** Agents see apps on the user's Mac through trycua's `cua-driver`, behind grants Zorvo owns (design and both spikes in `docs/superpowers/specs/2026-11-17-computer-use-design.md` on the branch `docs/computer-use-spec`). What exists: `src-tauri/src/computer_use/`. `driver.rs` finds the driver (`Zorvo.app/Contents/MacOS/cua-driver`; a debug build uses `src-tauri/binaries/cua-driver`, or `ZORVO_CUA_DRIVER_PATH`, which also skips the checks), checks it before every start (`check`: the app on disk is this Zorvo's version, else `UpdatePending`; the file's SHA-256 is the pin's and `codesign` accepts it for the pinned team, else `Changed`) and builds its command with `spawn::driver_command` and exactly the six variables of `driver_env` (`HOME` points into the data dir, so the driver reads no `~/.cua-driver` an agent could write). The pin is `src-tauri/resources/cua-driver.json`, never below 0.52.1 (before it the driver took the frontmost app at every start); `pnpm cua-driver:fetch` (run by `beforeDevCommand` and `beforeBuildCommand`) puts the file in `src-tauri/binaries/`, and `bundle.macOS.files` puts it in the app. `worker.rs` is `DriverClient`, the client of the driver's private worker (`cua-driver __private-worker --generation <id>`: one JSON object per line on stdin and stdout, no socket, protocol version 1 with `initialize`, `list`, `bind_session`, `close_session`, `call`). The worker answers one request before it reads the next and cannot cancel one, so the client keeps its own queue, writes one request at a time, and `abandon` drops a queued call but kills the worker for the running one (every other waiting call then ends `Exited`). `start` refuses another protocol version and a driver that is not the pinned release; `kill` waits for the child; a line over 32 MiB kills the worker. A driver session is bound per label (`driver::session_label`: the agent's name, numbered for a second session, since the driver refuses a label a live session has); the driver draws one agent cursor per session and shows the label only while two or more cursors are on screen. `state.rs` is `ComputerUse` (managed as `Arc`): the saved switch kept in memory (`save_app_state` calls `set_enabled`; off kills the driver) and the one shared driver, started on demand and killed in `RunEvent::Exit`. `permissions.rs` reads Zorvo's own Accessibility and Screen Recording (`AXIsProcessTrusted`, `CGPreflightScreenCaptureAccess`), asks for them only from `computer_use_request_permissions` and `computer_use_reset_permissions` (which runs `tccutil reset` for Zorvo's bundle id first), and builds `ComputerUseStatus` (`status_of`, pure; the driver part comes from `driver::check_for_status`, which reuses its answer while the file's size and modification time stay the same, since Settings reads the status on every window focus; a start always runs the full `check`). macOS applies a newly allowed Screen Recording only after Zorvo restarts, which Zorvo cannot detect, so `restartHint` is true once the user asked in this run and it still reads not allowed; `app_restart` (`app_update.rs`) restarts with no update, after the page's `writePendingBeforeRestart`. `computer_use_open_pane` takes only `"screen"` or `"accessibility"`. Frontend: `lib/computer-use.ts` (parsing, copy, `blockerOf`), `hooks/useComputerUseSetting.ts` (reads on mount and on window focus), `components/settings/ComputerUseSetting.tsx` and `ComputerUseGroup.tsx`; turning the switch on is the one place that asks macOS. Tests: `tests/it/computer_use_driver_test.rs` against `tests/fixtures/fake_cua_driver.mjs` (flags `FAKE_CUA_HANG`, `FAKE_CUA_FAIL`, `FAKE_CUA_HUGE`, `FAKE_CUA_PROTOCOL`, `FAKE_CUA_VERSION`, `FAKE_CUA_SLOW_MS`, `FAKE_CUA_CALL_LOG`), one ignored test that starts the real pinned driver, and `tests/fixtures/cua-driver-tools.json` (the pinned driver's tools and argument names, for the gate to come). **What an agent can do.** `gate.rs` holds `TOOLS`, the only tools listed and forwarded: `list_apps`, `request_access` (Zorvo's own), `list_windows`, `get_window_state`, `zoom` and `verify_state`, each with its own field list and Zorvo's own description (`tool_list`); any other name gets "Zorvo does not offer <tool>." (`get_accessibility_tree` is left out on purpose: it lists every app's windows and the driver removes it after 2026-11-26.) `protocol.rs` lists them for a caller with `Capabilities.computer_use`, adds `instructions.rs` to `initialize`, and hands a call to the gate unvalidated; `service.rs` gives it to `ScreenTools` (`computer_use::ScreenServer`, `server.rs`, attached with `set_screen_tools`) instead of the webview: the call still sits in the pending table (cap, 170 s, cancel), and `ScreenTools::ended` is told when it ends some other way. `AgentTools::note_profile` records each session's registry id (a fork copies its source's), which names the driver session. **The gate.** `rebuild` copies only listed fields, checked by kind; `session` and `max_image_dimension` are dropped, `screenshot_out_file` and `debug_image_out` refused, and no error repeats what the agent sent. `verify_state`'s `expect` passes only in the documented shape (`is_predicate`), and `since` only as "latest" or a snapshot this session read from that window (`Snapshots`). `check` resolves the `pid` (`apps::running`: `proc_pidpath`, the innermost `.app`, its identity, cached by pid and start time), needs a grant of this session for that app (`Grants::app_for`: same path and same identity as when the user answered) and a `window_id` that the driver's `list_windows` gives for that pid; after the read the pid's start time is compared again. **Apps and tiers.** `apps.rs` reads an app from disk: `Info.plist` (the `plist` crate), `codesign -dv`, and `codesign --verify --ignore-resources` against `anchor apple generic` (and `anchor apple`), so a team id is only trusted from a signature Apple issued; `resolve_bundle_id` asks `NSWorkspace`. `tiers.rs` is the table (`Never`, `ViewOnly`, `ClickOnly`, `Full`): an entry matches a signing identifier or a bundle id, or a part of one ("com.google.Chrome.helper"), whoever signed the app, since a restricting entry can only restrict a copy that claims its name; `warning_of` gives a row's warning. **Asking.** `requests.rs`: `validate` (1 to 10 bundle ids, a reason of at most 500 characters), `rows_for` (each bundle id resolved on this Mac; the agent's text is never an app's name), and `Requests`, one card on screen per session with the rest queued. Tests: `tests/it/computer_use_e2e_test.rs` (a client on the tool socket, the gate and the fake driver), unit tests in each module. Not built: acting (click, type), full screen, the command path's tool note for Pi, and `zorvo tools` listing these tools.

**Spawning processes.** Every process Zorvo starts goes through `src-tauri/src/spawn/`: `spawn::command` and `spawn::pty_command` run the program through Zorvo's own executable in its `disclaim-exec` mode (`posix_spawn` with the private `responsibility_spawnattrs_setdisclaim` and `POSIX_SPAWN_SETEXEC`, found with `dlsym`), so the program is its own macOS responsible process and never inherits Zorvo's Screen Recording or Accessibility grants (a plain child does: the computer-use spike saw a child's `screencapture` succeed). `spawn::driver_command` is the one exception, for the computer-use driver. `src-tauri/clippy.toml` disallows `std::process::Command::new` and `portable_pty::CommandBuilder::new` elsewhere; integration tests allow them (`tests/it/main.rs`). `lib.rs::run` sets the trampoline to `current_exe()`; without it (unit tests, the CLI modes) programs start directly. `main.rs` runs `disclaim-exec` before the agent-environment guard, since it only takes privileges away. Tests: `tests/spawn_test.rs`, a test binary of its own since the trampoline is process-wide.

**Threading rule for Tauri commands.** Commands that touch the filesystem, the login shell or a child process are `#[tauri::command(async)]` so they don't freeze the window. `send_input` stays sync so a terminal's keystrokes reach the PTY in order: async would run them on a thread pool where they could arrive out of order. `end_orphaned_sessions` is sync for the same reason (sync commands run on the main thread in the order the webview sent them, so its list of orphans is taken before any later start registers); it only lists sessions there and ends them on a thread of its own.

## Testing conventions

- Frontend tests live in `src/test/` (Vitest + Testing Library, jsdom). `src/test/setup.ts` fakes Tauri `invoke`, including an in-memory store seeded via `window.__FAKE_TAURI_STORE__` and canned ACP responses; agent profile fixtures are in `src/test/fixtures/agents.ts`.
- Rust tests are in `#[cfg(test)]` modules and `src-tauri/tests/it/` (one binary; a new file needs a `mod` line in `main.rs`, which a test checks).
- `src/test/tauri-contract.test.ts` checks the wiring the fake backend and the Rust tests both miss, by reading the source of both sides (the frontend with the TypeScript compiler API, the Rust with a small scanner in `src/test/helpers/tauri-contract.ts`). Every `invoke('name', { keys })` must name a command in `generate_handler!`, pass only keys that are parameters of its `#[tauri::command]` fn (camelCase of the snake_case name) and all of its non-`Option` parameters (a key passed only inside a conditional spread is allowed but does not count as passed). Every `listen`/`once` event must be emitted by Rust or by the frontend, and every event Rust emits must be listened to or listed in `EVENT_ALLOWLIST` with a reason. A call whose command name is not a literal goes in `NON_LITERAL_CALLS` with the commands it can reach; a stale entry fails too. When it fails after you add a command, an argument or an event, fix the name or key, or the table, not the check. It does not check argument types or values. `helpers/tauri-contract.test.ts` tests the extractors and each assertion on small inline snippets. The scanner refuses `rename_all` and destructured parameters, so a command that needs either needs the scanner taught first.
- Agent worktrees under `.claude/` contain copies of the repo; Vitest and ESLint both exclude `.claude/**`.

## Working in worktrees and keeping disk use down

Parallel sessions each work in their own git worktree under `.claude/worktrees/`; two sessions in the main checkout share its files and its current branch. `node_modules` costs almost no disk there (pnpm clones its store's files on APFS, so `du` overstates it); the Rust `target` folder is what costs real disk (about 1.5 GB) and build time.

- **One shared Rust target.** On the maintainer's Mac an untracked `.cargo/config.toml` at the repo root (hidden through `.git/info/exclude`) holds `[build] target-dir = "/Users/mac/Library/Caches/zorvo-target"`. Write the absolute path: cargo does not expand `~`, and would build into a folder literally named `~` inside the repo. Cargo reads the file from every worktree below the repo folder, so a new worktree compiles only the `zorvo` crate (about 35 s) instead of every dependency (a cold build took about 9 minutes). Leave the file alone: `git clean -x` would remove it, and every worktree would silently go back to its own `target`. Builds from several sessions queue on cargo's file lock, and `pnpm clean:rust` empties the shared folder for all of them, so don't run it while another session builds. Deleting the folder is safe: the next build recreates it. Without the file (CI, another machine, a worktree outside the repo folder) each checkout builds its own `target`; run `pnpm clean:rust` there once its PR has merged or its session is done.
- **Run only what the change needs.** `pnpm lint` and `pnpm test` for anything under `src/`. Add `cargo fmt --check`, `cargo clippy --all-targets -- -D warnings` and `cargo test` only when `src-tauri/**` changed (CI also runs them for `package.json`, `pnpm-lock.yaml` and `.nvmrc`). A docs, site or copy change needs no cargo, and no new worktree either when no other session works in the main checkout: use a branch there.
- **Review before the push.** Review the diff and fix what it finds before pushing (Claude Code: `/code-review --fix`), so CI runs once on a reviewed change.
- **After a merge,** update local `main` and run `git worktree list`: `git worktree remove` any worktree left for a merged branch. The app's auto-archive on PR close (on for the maintainer) archives the session and, per the app, removes the worktree it made unless that holds uncommitted changes. A worktree made with `git worktree add` is yours to remove.

## Design system rules (enforced by tests)

- `src/styles/globals.css` is the source of truth: its `@theme` block holds dark values and generates Tailwind utilities (`bg-surface-2`, `text-fg-muted`, `border-border-strong`); a `prefers-color-scheme: light` block overrides them. Change `globals.css` and `docs/design-system/tokens.json` together — `design-system-docs.test.ts` fails on drift. `ground`, `sheet` and `chip` are the v2 surfaces (the window, the raised chat and inspector, and translucent fills); `sheet-fills.test.ts` fails on `bg-bg` or `bg-surface-1` in any component: no screen uses the old two surfaces.

## Project rules

- The app never asks for or stores the user's API keys/tokens; agents sign in with their own tools. The one exception is Private mode (opt-in), whose backend keeps these Keychain items under the service `xyz.zorvo.desktop.private` (a debug build adds `.` and 8 hex characters of a hash of the app data dir, so scratch `HOME`s never share one; `device.rs`'s `keychain_service`): the device secret (`device-secret`), the next secret while a restore hands over (`device-secret-next`), the NEAR AI key (`nearai-key`), a key the user pasted (`nearai-own-key`), and a capped session's key (`nearai-session-<app session id>`), plus `<app data>/private/state.json` (recovery flags, the pending top-up, the last balance and model list, the recorded private sessions, and capped sessions' Worker ids in `sessionCaps`; no secret). The CSP (`tauri.conf.json`) allows only the local IPC bridge — the main webview makes no network requests, and of Private mode it sees only codes, statuses and, by design, the recovery code (`private_recovery_code`, `private_recover`). An artifact's page, in its own webview with its own CSP, may load scripts and fonts from the hosts listed under **Artifacts** and nothing else. The backend makes only these kinds: it reads the ACP registry, on **Install** it downloads from the hosts that install needs (listed in the README's privacy section; when Zorvo opens it also installs, without a click and once per run, the npm package of an agent the user has used that has none in Zorvo's folder yet), it checks `latest.json` in this repository's latest release for a newer Zorvo (shortly after start, then daily) and downloads that update from GitHub when the user clicks **Update & restart**, and it calls the Zorvo Credits Worker (`CREDITS_BASE_URL` in `src-tauri/src/private_mode/mod.rs`, from `ZORVO_CREDITS_URL` at build time; Rust only, the device secret as bearer): `private_status` at start once this Mac has a device, plus following a top-up still pending from before when there is one (`private_topup_status` every 3 s, every 15 s while a paid one waits for stock, less and less often, at most 5 minutes apart, while the Worker cannot be reached, until it settles, a lasting error ends it, or the cap stops a waiting one the Worker cannot answer about, 10 minutes after its hold ends), and stock, models, top-ups, promo codes, restores, and a capped session's create/end/seen/raise routes once the user opens Settings → Private mode or turns a draft's Private chip on. It also forwards a private session's model requests to NEAR AI Cloud (`cloud-api.near.ai`) through the loopback proxy, with the key the proxy holds (the Worker never sees prompts); the signature and attestation reads of B2 use the same host, and `private_check_own_key`/`private_set_own_key` check a pasted key there before the Keychain keeps it. With `settings.paymentSource: "ownKey"` the launch passes `privateOwnKey`, the proxy gets the pasted key, the MCP balance answer says that balance is not visible, and the low-credit warning is off; a 402 while checking the key still saves it with a warning. It also runs the user's own `gh` (pull requests, and the GitHub connection's sign-in state), which makes its own requests; Zorvo sees only what `gh` prints and stores none of it. It also listens on a private Unix socket in the app data dir (or a short `/tmp` path) for its own `mcp-bridge` process (see **Agent tools**); that is local and uses no network.
- Prefer a focused hook in `src/hooks/` or a helper in `src/lib/` over growing `App.tsx`.
- Conventional Commits (`feat:`, `fix:`, `refactor:`, `docs:`, `test:`, `chore:`, `ci:`); branches `feat/…`, `fix/…`, `chore/…`. Add a line under `Unreleased` in `CHANGELOG.md` for user-visible changes.
- Release: bump the version in `package.json`, `src-tauri/Cargo.toml` and `src-tauri/tauri.conf.json`, roll the changelog, then push a `vX.Y.Z` tag; the Release workflow builds a universal macOS app, then `node scripts/sign-release.mjs vX.Y.Z` on your Mac signs the update and fills a draft release.
- xterm 6 broke under esbuild's syntax minifier (Vite 6). Vite 8 builds with Oxc, which keeps it working; `xterm-release-build.test.ts` builds xterm as the release does and checks the terminal still answers. Don't remove it, and run it after changing the minifier or the build target.
