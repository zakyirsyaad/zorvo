# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

Zorvo (formerly Agent Desktop) is a macOS Tauri 2 app that hosts other coding agents. Qwen Code, Claude Code, Codex and the other agents come from the ACP registry and are driven over the Agent Client Protocol (ACP, JSON-RPC over stdio) and shown as a chat UI. Pi comes through the registry's `pi-acp` adapter. A PTY is used to run an agent's own terminal sign-in and the shells of the workspace terminal. React 19 + Tailwind 4 frontend in `src/`, Rust backend in `src-tauri/` (crate `zorvo`, lib `zorvo_lib`). Package manager is pnpm; Node comes from `.nvmrc` (26), which CI and the release workflow also read.

## Commands

```bash
pnpm install
pnpm tauri dev              # run the app (Vite on :1420 + Rust backend)
pnpm lint                   # tsc --noEmit + eslint --max-warnings=0
pnpm test                   # all Vitest tests
pnpm vitest run src/test/persistence.test.ts          # one file
pnpm vitest run src/test/persistence.test.ts -t "name" # one test
pnpm design-system          # local design-system reference on :5180
pnpm registry:update        # refresh the bundled ACP registry history (src-tauri/resources/registry-history.json)
pnpm tauri build            # production bundle (the only build that applies the CSP); signs the update package, so it needs TAURI_SIGNING_PRIVATE_KEY (+ _PASSWORD) or --config '{"bundle":{"createUpdaterArtifacts":false}}'
node scripts/sign-release.mjs vX.Y.Z   # on the maintainer's Mac, in a clean checkout of the tag, after its Release run is green: sign and fill the draft release (see `docs/development.md`, "Releasing"); --dry-run writes nothing; run it with node, not pnpm (pnpm run puts node_modules/.bin first on PATH)
pnpm clean:rust             # cargo clean for src-tauri (empties the shared target, see "Working in worktrees")
```

Rust (from `src-tauri/`; `pnpm build` must have produced `dist/` first, since Tauri embeds it at compile time):

```bash
cargo fmt --check
cargo clippy --all-targets -- -D warnings
cargo test
cargo test --test it acp_manager_test::            # one integration test file
cargo test --test it acp_manager_test::some_name   # one test
```

Integration tests are modules of one binary, `tests/it/main.rs` (a new file needs a `mod` line there), so they share a process and run in parallel threads. A test that sets process-wide state gets its own file in `tests/`, like `installer_state_test.rs`.

The Rust ACP tests spawn `src-tauri/tests/fixtures/fake_acp_agent.mjs` with Node, so Node must be on PATH. Its flags add capabilities on top of its defaults (`loadSession`, `fork`, `delete`): `FAKE_ACP_RESUME` (`session/resume`), `FAKE_ACP_LIST` (`session/list`), `FAKE_ACP_LIST_PAGES` (pages from a JSON file), `FAKE_ACP_LIST_FAIL_AT=<n>`, `FAKE_ACP_CALL_LOG` (every method received, one per line), `FAKE_ACP_SLOW_REPLAY` (a load replay that pauses mid-way) and `FAKE_ACP_WRITE_FILES` (a JSON object of relative paths and contents, written into the session's folder when a `permission` prompt is answered allow, and by `crash` just before it exits) and `FAKE_ACP_SETUP_METHOD` (also offers Qwen Code's older terminal method, which marks an interactive setup), `FAKE_ACP_PARAMS_LOG` (appends `{method, mcpServers}` for every `session/new`, `session/load`, `session/resume` and `session/fork`) and `FAKE_ACP_MCP_CALL` (JSON `{tool, args}`) with `FAKE_ACP_MCP_LOG` (a prompt `mcp` makes the agent act as an MCP client: it spawns the first `mcpServers` entry its session was opened with, runs `initialize`, `tools/list` and that `tools/call`, logs each result and says `mcp:<text>`, or `mcp:none` when the session had no server), `FAKE_ACP_ENV_LOG` (at start, one JSON line saying which of `ZORVO_MCP_SOCKET`, `ZORVO_MCP_TOKEN` and `ZORVO_TOOLS` are set, never their values) and `FAKE_ACP_TOOLS_COMMAND` (JSON `{tool, args}`, with `FAKE_ACP_MCP_LOG`: a prompt `tools` makes the agent run the program in `ZORVO_TOOLS` as `tools <tool> <json>` and log `{status, stdout, stderr}`). CI runs all of the above except `cargo fmt` (lefthook runs that pre-commit if installed with `pnpm lefthook install`).

## Architecture

**Frontend ↔ backend.** The UI calls Tauri commands (all registered in `src-tauri/src/lib.rs`'s `generate_handler!`) and listens to events: `acp-event` (one channel for every ACP session, payload `{sessionId, kind: update|permission|elicitation|elicitation-complete|turn-end|exit, ...}` built in `acp/commands.rs`) and `sign-in-terminal` (output and exit of an agent's terminal sign-in, see below).

**Session engine.** Every session is an ACP chat, run by `src/hooks/session-engine/useAcpEngine.ts`. ACP updates are folded into chat messages by `src/lib/acp-events.ts`; modes/models/config options come from the agent at session start (`useAcpSessions.ts`, `lib/acp-draft.ts`). Saved terminal sessions from older versions are dropped on load (`dropTerminalSessions` in `lib/persistence.ts`).

**Agent profiles are the trust boundary.** ACP agents come from `src-tauri/src/registry/`: the official ACP registry, fetched by the Rust backend (never the webview) at startup when the last fetch is over 24 hours old and on **Check again**. It keeps a dated version history, and a version is offered only after it has been listed for 7 days. A history is bundled with each release (`pnpm registry:update` regenerates `src-tauri/resources/registry-history.json`). Agents in use are `settings.enabledAgents`, the version in use is `settings.agentVersions`, and installed agents are enabled once automatically. Settings' **Check again** lives in the Agents section. The webview only ever sends an agent id (and folder); `acp/commands.rs::launch_for` turns the id into a command line. Never let the UI pass a raw command or args. An entry may offer several distribution kinds (`binary` plus `npx`, as kilo and sigit do); `registry/schema.rs::choose_distribution` picks one at parse time, so everything downstream still sees one `Distribution` per entry (the history stores only the chosen kind). Preference: a pinned `npx` package, then a pinned `uvx` package, then a binary with a build for this Mac and a valid checksum, then a binary with no build for this Mac (shown as unsupported). A package comes first because it does not depend on this Mac's platform (the choice frozen in the history is the same everywhere), because a binary is first looked up on `PATH` by its program name (`binary_program` in `resolve.rs`) and an unrelated program of that name would run as the agent, and because Zorvo may not unpack a binary's archive format. Each candidate must pass `is_valid_entry` unchanged: the choice only picks among valid candidates and a candidate that fails contributes nothing (no args, no env). One rule is looser than before, on purpose: a missing or `null` `sha256` on a platform other than this Mac's no longer drops the whole entry (`sha256_or_empty`; only `current_platform()`'s target is ever read, and an empty checksum never validates), and each kind of an entry is read on its own, so one malformed kind cannot hide a valid one. `RegistryEntry`'s derived `Deserialize` is for Zorvo's own files only and must never read raw registry data. An entry that fails every candidate is not offered but reported as unavailable (`UnavailableAgent`, reason `no_checksum` when this Mac's binary publishes no valid checksum, else `invalid_entry`; entries with no usable or a reserved id are left out of both lists).

**Agent catalog.** Settings → Agents and the welcome screen (`components/Onboarding.tsx`, its rules in `lib/onboarding.ts`: rows in use or on this Mac first, then the popular ones, five until Show all; ticking only puts the agent in use (`withAgentAdded`), a ticked agent that is not installed shows Install, which calls `addAgent`, and unticking only takes the agent out of use and cancels its install) read one read model: `get_agent_catalog` returns `Catalog::catalog_view` (in `registry/mod.rs`; its types are in `registry/catalog_view.rs`) with each registry agent's availability (including `unsupported` for a binary agent with no build for this Mac's target), install state and offered update. Recorded versions under 7 days old are ignored. `update_agent` (`installer/commands.rs`) is the only way an agent's version changes; the target comes from `Catalog::update_target`, never the UI. Logos: `registry/icons.rs` fetches SVGs from the registry CDN into the app data dir (only allowed URLs, SVG bodies only) and `get_agent_icons` returns data URLs, falling back to the bundled `src-tauri/resources/registry-icons.json` (`pnpm registry:update --icons-only` regenerates it). Frontend: `components/agents/` (`AgentCatalog`, `AgentCatalogRow`, `AgentCatalogPanel`), `hooks/useAgentCatalog.ts`, `useAgentCatalogActions.ts`, `useAgentUpdates.ts` (badge, and `settings.notifiedUpdates` for the once-per-version notice), `lib/agent-catalog.ts`, `lib/agent-icons.ts`. `AgentCatalog.unavailable` lists what the registry offers but Zorvo cannot (`parse_registry_report` output, kept in `registry-cache.json` as `unavailable`, `CatalogState::unavailable_agents`: sorted and deduped by id when stored, not in `agents`, no install or add path, and an id the history already has stays a normal row; a cache without the field counts as stale, so the next start fetches again). The UI shows it as a collapsed "Not available (N)" section (`components/agents/UnavailableAgents.tsx`, wording in `unavailableReasonText`), searched with the rest and opened while a search is typed. The bundled history is the raw registry, filtered by the same parser at load, so it needs no regeneration when the rules change. A removed agent's saved sessions, once stopped, show `RemovedAgentPanel` with **Add <Agent>**. `usePersistedState().saveNow` flushes state before a catalog action reads it and rejects when the write failed; writes run one at a time, and `AppStore::save_state` holds a lock around `state.json`.

**App updates.** `app_update.rs` holds `app_update_check`, `app_update_install` and `app_update_restart` (plain `#[tauri::command]` on `async fn`), built on `tauri-plugin-updater` used only from Rust (`UpdaterExt`), so the webview needs no `updater:*` permission (a test keeps it out of `capabilities/default.json`) and sends no URL. The endpoint (`latest.json` of this repository's latest release), the public key and `requireSignedVersion` are in `tauri.conf.json` `plugins.updater`: a download is installed only if its signature matches that key and records the version `latest.json` announces, and `is_allowed_download_url` (`ALLOWED_DOWNLOADS`) refuses a manifest whose package is not on `api.github.com` or `github.com` inside this repository (renaming it needs a release that accepts both names first, since installed copies carry the list; copies up to 0.7.0 only accept zorvo-releases, which is why `docs/development.md` has "The first release from this repository"). The client from `updater()` is https-only with connect, read and check timeouts, and `app_update_install` caps the download at 20 minutes. Both commands do nothing outside an app bundle (`runs_from_app_bundle`): under `pnpm tauri dev` or a bare `target/release/zorvo` the plugin would swap out the folder holding the executable, which is the cargo target; Tauri gives no executable path when a folder above it is a symlink, which also ends the check (logged on stderr). A check keeps the found `Update` in `PendingAppUpdate` (ignored while an install runs and after it); a manifest the download policy refuses counts as no update (`Ok(None)`), not as a failed check; failures of a check or an install are written to stderr, which only shows when Zorvo is started from a terminal (a Finder launch discards it). Install holds `PendingAppUpdate.install`, an async lock released on every path (a second call, from a page reloaded meanwhile, waits for the first and then finds the update installed), emits `app-update-progress` (`{phase: downloading|installing}`, `installing` before the signature is checked), installs and returns without restarting; calling it again after a success does nothing. The restart is its own command because `AppHandle::restart` ends the process without closing the page, so `pagehide` and `beforeunload` never fire: `useAppUpdate.install` calls install, then `beforeRestart` (`App.tsx`: `saveNow()` and the transcripts' `flush()`, which rejects when a write failed or a transcript is still loading, and then Zorvo stays open), then `app_update_restart`, which exits through `RunEvent::Exit` (workspace shells end; Zorvo never stops ACP agents on any exit). Frontend: `hooks/useAppUpdate.ts` (first check ~8 s after start, then daily, or after 15 minutes when a check could not be made; a failed check is silent, a failed install or save goes to `setNotice`; Later hides one version for this run; an answer arriving during an install is ignored), `components/AppUpdateNotice.tsx` (says what a restart ends: `busyCount` agents mid-turn and `terminalCount` live shells, worded by `restartWarning`), `lib/app-update.ts`; only the main window mounts `App`, so popouts never check. Releases are signed on the maintainer's Mac, never in GitHub: the Release workflow only builds (job `macos`, which runs the project's dependencies, so it holds no secret but the optional `APPLE_*` ones and publishes nothing) and keeps the DMG and the `.app.tar.gz` as the `release-build` artifact (30 days), under names made from the tag. The updater key, its password and any token that can publish releases are not GitHub secrets at all (a repository secret is readable by any workflow in the repository; the account's plan has no environments with reviewers, which was the first design). The build job gets a one-off key made on the runner, because `tauri build` refuses to run without one while `createUpdaterArtifacts` is on and `--no-sign` would also skip Apple code signing; the signature it makes is discarded. `node scripts/sign-release.mjs vX.Y.Z` does the rest (not a package script: `pnpm run` puts `node_modules/.bin` first on PATH), from a clean checkout of the tag. It proves HEAD, the tag on GitHub (`remoteTagCommit`) and the commit the newest successful run built are the same, reads the config and changelog once, downloads the artifact from that run with the maintainer's own `gh` login (`release-github.mjs`'s `downloadBuild`, which on a reset connection, timeout, EOF or 5xx tries again, 3 tries in all with a growing pause and an emptied directory, and says so on screen; any other failure ends it, and the last try's error is the one shown), checks it as data (`release-checks.mjs`: exactly the two expected files, a gzip package that holds only `Zorvo.app` with no hard links or links out of it, and an app binary that holds `tauri.conf.json`'s updater pubkey as text, a tripwire against a build that trusts another key, not a boundary), lists what changed since the last release tag in the dependencies, workflow and scripts and asks to go on, asks for the password hidden (never from the environment), signs with `tauri signer sign --app-version` using the CLI pinned in `scripts/updater-signer` (`signer-cli.mjs`: `npm ci --ignore-scripts` every time, run by `process.execPath`, kept equal to the root lockfile's version by `scripts/updater-signer.test.mjs`, so no project dependency runs next to the password), checks `latest.json` (`scripts/updater-manifest.mjs`: the six entries `tauri-action` wrote, with the package's asset API URL, which exists only after the upload) with `scripts/check-updater-signing.mjs manifest`, the package and the download policy before any write to GitHub, then makes or refills the draft release and uploads. The checkout is checked again before signing and before uploading. It passes the key's path to the CLI and never reads the file; the password goes only into the CLI's environment, and the project's folders and the key's variables are dropped from PATH and the environment of everything else. `--dry-run` writes nothing to GitHub. Not covered, said plainly in the README: a build compromised during a release that is then signed (the DMG too), and other code running as the maintainer on the Mac. `scripts/release-workflow.test.mjs` fails when a change gives the build job a secret other than `APPLE_*`, a token or a way to publish. The `macos` job still checks the tag against the three versions, and that CHANGELOG.md has a section for it, before it builds. `check-updater-signing.mjs key` checks a key with the pinned CLI. Never create, read or print the private key.

**Installer** (`src-tauri/src/installer/`). Zorvo installs an agent the user picks, plus Node.js or uv when it needs them, under the app data dir's `tools/`. Runtimes are pinned with their SHA-256 in `src-tauri/resources/runtimes.json` (`pnpm runtimes:update` regenerates it); every download is checked against a pinned hash, archives unpack with path and size checks, and each install is written to `tools/staging/` and renamed into place. Commands: `install_agent`, `install_runtime`, `cancel_agent_install`, `remove_agent_install`; progress goes out as `agent-install-progress`, and `agent-profiles-changed` follows every install. The plan is rebuilt in the backend from the agent id, never taken from the UI.

**ACP backend** (`src-tauri/src/acp/`): `jsonrpc.rs` framing, `connection.rs` one agent process, `manager.rs` maps app session ids onto ACP sessions. `reopen` (`acp/manager/reopen.rs`) continues a session with `session/resume` when the agent offers it, else with `session/load`. One agent process can host several ACP sessions (a native fork lives in its source's process), so connections are shared and killed only when their last session stops. Auth-required errors are surfaced to the UI as `ACP_AUTH_REQUIRED:` + JSON (parsed in `src/lib/acp-auth.ts`), both when a session opens and when a prompt is refused (Claude Code's adapter opens sessions signed out and refuses only the prompt).

**Session list and import.** `acp/session_list.rs` reads every page of the agent's `session/list` in one process (10 pages, 200 sessions), validates each `SessionInfo`, and ends the agent. The new-session draft offers what it lists through `useAgentSessionList` and `AgentSessionList`; `useSessionImport` records the session before `acp_import_session`, and `useAcpEngine.importSession` folds the load replay with `applyReplayUpdate`. The backend routes that replay through a notification-only `replaying` map, so a request during the import cannot deadlock; a resume-only import gets `historyElsewhere`, and the chat says the earlier messages stay in the agent.

**Models.** An agent may report its models in the session answer's `models` field (`{ currentModelId, availableModels: [{ modelId, name, description? }] }`, Gemini CLI does) instead of a model config option. `toModels` (`useAcpSessions.ts`) validates it into `AcpSessionInfo.models`, the probe returns it (`acp/probe.rs`, `useAgentProbe`) and `AgentOptions.models` remembers it. `acpControls` makes the composer's model chip from a `model` config option when there is one, else from `models`; Codex and Qwen Code report both, and for them the option carries every pick, so `changesToApply` ignores a `models` pick when `hasModelConfig` says the agent has an option (`models.currentModelId` only follows `setModel`, so after an option pick it is the model the session started with). A pick goes out as `acp_set_model` (`AcpManager::set_model`, the unstable `session/set_model` with `sessionId` and `modelId`; the spec's draft schema no longer documents it, Gemini still answers it); the UI sends only the ids. In a draft the pick is `AcpChoices.modelId`, remembered as `AgentOptions.preferredModelId` (`withPreferred`, while the agent still offers it) and applied by `changesToApply` as a `{ kind: 'model' }` change before the first prompt. A reopened session's answer may omit `models` (a `session/resume` answer does); then the remembered ones stay, the running session has no chip, and a pick is still sent as it is (`reopenedWith` in `changesToApply`), where the agent refuses a model it does not know. Gemini CLI's `session/load` does report them, but with `currentModelId` back at its default (`auto`, which can hang) whatever the session ran on, so a resume applies the remembered pick again before the first prompt (`startChoices` in `App.tsx`'s `resumeSession`). `FAKE_ACP_MODELS` makes the fake agent report models and answer `session/set_model`.

**Composer controls from the agent.** `acpControls` (`lib/composer-controls.ts`) turns what the agent reports into chips. Modes, models and config choices keep their `description`; a mode whose id or name matches `RISKY_MODE` gets `risky`, which the open menu marks with a `ShieldAlert`. A model called "Default" with a short description shows as "Default (Opus)". Every `select` config option outside the categories `mode`, `model` and `thought_level` with at least two choices becomes an `ExtraControl` (Codex `collaboration_mode`, Claude `fast` and `agent`): a chip that sends `acp_set_config_option` like the effort chip and goes through `changesToApply` as a config pick. Only `model`, `thought_level` and `model_config` picks are remembered for the next session (`REMEMBERED_CATEGORIES`), so Plan or a persona never carries over. An agent reports the effort list of the model it runs only, so `AgentOptions.effortsByModel` keeps each model's `thought_level` option as reported (`withReported` for a session's report or a pick, `withEffortList` for a probe), and a draft on another model shows that model's list (`listsForModel` in `draftInfo` and `withPreferred`), or no effort chip while it is unknown, never the reported model's; a pick its list lacks is not shown, and `withPreferred` keeps a remembered effort for a model whose list is unknown, since `changesToApply` checks it against the agent's list once the model is set. A list over 10 choices gets a search field. `SAFE_MODE_IDS` puts `workspace-write` before `read-only`; Codex's default `agent` ("Auto review") is deliberately not risky (pinned in `acp-modes.test.ts`).

**Probing a draft's agent.** ACP agents report modes/models/efforts/slash commands only inside a session, so `acp/probe.rs` (`acp_probe_agent`) asks in a short-lived process. Opening a session can run the user's session hooks and lands in the agent's history, so it opens one only to learn a never-run agent's options or to check the sign-in of an agent that cannot report it, and deletes it in the background (`session/delete`, else `session/close`). An agent that pushes `_auth/status_update` (Claude Code) and whose options are known is only asked who is signed in. `signInChecked` in the result says whether the sign-in was actually seen. Opening a session proves nothing for an agent that cannot report its sign-in and refuses only the prompt (GLM Agent), so for an agent without `_meta.authStatus` the probe also checks the variables its `env_var` methods name (`missing_key_variables` in `acp/key_env.rs`): a variable counts as set when it is non-empty in the launch environment or in Zorvo's own; only presence is read, never the value. An agent that also offers a `terminal` method, or one `env_var` method with all its required variables set, is left alone. Otherwise `signInChecked` is false and the answer's `missingEnv` holds the names (`useAgentProbe` keeps only valid variable names); Check sign-in and the draft check then drop a recorded Ready (`markUnconfirmed`), so the chip reads Not checked, not Sign in, and Settings' row says which variable to set (`unconfirmedMessage`). `src/hooks/useDraftAgentCheck.ts` drives it for a new-session draft (via `useAgentProbe`), keeps the sign-in panel in step and asks again on window focus while a sign-in is pending; results are merged with `withProbed` (`lib/acp-draft.ts`), which never overwrites what a real session reported.

**Terminal sign-in.** Zorvo advertises `auth.terminal`. `acp_start_terminal_sign_in` reads a `type: "terminal"` method from a fresh `initialize` (`acp/terminal_auth.rs`, same env deny list as the registry) and runs the agent's own program plus the method's args in a PTY with a `signin-` id. Its output goes on `sign-in-terminal`. `useAgentSignIn` re-checks with the probe and sends the refused message through `retryAfterSignIn`. `authenticate` is never sent for a terminal method. **Agent setup:** a method in the older form, with no `type` and `_meta.type: "terminal"` (Qwen Code's only one: `openai`, `_meta.args: ["--auth-type=openai"]`), marks the agent's own interactive setup, where it picks its provider. `acp_start_agent_setup(profileId, cwd, terminalId)` (`acp/commands.rs`) runs it only when a fresh `initialize` reports one (`has_interactive_setup`, `AcpManager::agent_setup_with` in `acp/terminal_auth.rs`). It runs the agent's own program from the registry without the entry's own arguments (`AgentProfile.setup_args`, filled in `registry/resolve.rs`) and without the method's `args`, in the sign-in PTY under a `signin-` id. The UI sends no method, command or argument.

**Which agents are ready.** An agent counts as signed in only when it was seen so: `useAgentSignInStatus` (memory for `needed`, `settings.signedInAgents` for the rest, which the backend `Settings` also keeps) is told by `useDraftAgentCheck` when a probe shows someone signed in, by `useAgentSignIn` when a sign-in or **Check again** takes, and when an agent asks for a sign-in (`requestSignIn`). The sidebar chip (`lib/agent-sign-in.ts`) reads Ready, Sign in or Not checked; Zorvo never asks every agent at startup, since a probe can open a session in the agent. ACP gives `-32000` the meaning "authentication required" but fixes no message, and the spec has no way to ask whether anyone is signed in. So a refusal counts as a sign-in request (`is_auth_required` in `acp/manager.rs`) when it is `-32000` and either its message has a word in `SIGN_IN_WORDS` (including "API key" and "credential", as Gemini CLI words it), or the agent offered sign-in methods in `initialize` and the refusal answers `session/new`, `session/load`, `session/resume` or a prompt; `session/list` needs the wording. A `-32000` from an agent with no methods stays a plain error. A `-32603` ("Internal error") counts too, but only when the agent offered methods, the refusal answers one of those requests, and its `message`, a text `data`, `data.details` or `data.message` has a whole sign-in word or two-word phrase (`mentions_sign_in_phrase`: `SIGN_IN_WHOLE_WORDS` such as "unauthorized" or "apikey", `SIGN_IN_PHRASES` such as "log in" or "API key"; letters inside another word, as in "designing" or "catalog in", do not count, unlike the looser letters-only `SIGN_IN_WORDS` check of `-32000`) (GLM Agent opens sessions without a key and fails the first prompt with `-32603` and "No API key found" in `data.details`); any other `-32603` stays a plain error. The rule lives in `acp/manager/sign_in.rs`, with its unit tests, and `FAKE_ACP_PROMPT_ERROR_DETAILS` makes the fake agent refuse prompts that way. Methods Zorvo cannot run (`explain` in `lib/acp-auth.ts`: keys, Vertex AI, gateway) get text, never a button, and the panel's **Check again** (`auth.recheck`) re-asks through `checkSignIn`, after `refreshLoginEnv` (`lib/sign-in-check.ts`: the `refresh_login_env` command, which only calls `env_resolver::refresh_user_env()` and returns nothing; `launch_for` only ever reads the cached environment, so without it a key exported in `~/.zshrc` after start is never seen; it is not `get_agent_profiles(refresh: true)`, which also refetches the registry and runs `npm`). Settings' **Check sign-in** does the same first: a failed re-read does not stop the probe, the status reads "checking" meanwhile, and a request dismissed or replaced during it ends the check. The sweep never refreshes. `requestSignIn` returns false, and the caller says so (`onSignInBlocked`, or `startSignIn` returning false), when another agent's sign-in is running; `authRequest` is one slot shared by the draft panel, sessions and Settings, so never `dismiss()` a request that carries `pending`. `AuthPanel` says the returned message is sent again only while `pending` is set (`hasReturnedMessage`), puts its progress and result lines in one always-mounted `role="status"` (a failure reason only through `plainReason`, `lib/agent-sign-in.ts`, shared with Settings), and `SignInLayer` keeps a second, sr-only live region mounted before the panel to announce it. **File viewer.** The Files tab (`components/FilesPanel.tsx`) marks changed files and their folders (`lib/file-markers.ts`, from `useInspector`'s HEAD stats with `filesPrefix`, since stats name repository paths), and a click opens `components/files/FileViewer.tsx` in the tree's place (`useInspector.viewedFile`; another folder closes it; the inspector widens like the Terminal tab). **Agent tools.** Groundwork for Zorvo's own MCP server, so an agent can call tools such as `delegate` (`src-tauri/src/agent_tools/`; design in `docs/superpowers/specs/2026-11-13-zorvo-mcp-tools-design.md`). All five tools work: `list_agents`, `delegate`, `start_session`, `read_session` and `stop_session`. **Bridge:** the executable has a second mode, `zorvo mcp-bridge` (`bridge.rs`, checked in `main.rs` before Tauri starts, so no window opens). An agent starts it as a stdio MCP server; it reads `ZORVO_MCP_SOCKET` and `ZORVO_MCP_TOKEN`, sends the token as a first line and then only copies bytes both ways (the MCP is spoken by the backend). It prints at most one plain line on stderr and never the token. **Socket** (`socket.rs`): `<data dir>/agent-tools/s.sock`, or a short `/tmp/zorvo-<uid>-<hash>/s.sock` when that path would not fit in a socket address (100 bytes); the directory is 0700 and owned by the user (checked), the socket 0600, a socket left by a dead run is replaced after a failed connect and a live one is never taken over, and dropping the listener removes the file. A connection must send a known token within 2 s (first line at most 4 KiB), otherwise it is closed. **Tokens:** one random 32-byte hex token per app session (`Tokens::issue`, compared in constant time against every stored token), in memory only, never logged or written; `forget` ends it with the session. **MCP subset** (`protocol.rs`, pure `handle_line`): `initialize` answers with the client's `protocolVersion` when it is in `SUPPORTED_VERSIONS` (`2025-11-25`, `2025-06-18`, `2025-03-26`, `2024-11-05`), else the newest; `ping`, `tools/list` and `tools/call` work, and `tools/call` serves the five tools in `tools.rs` (`list_agents`, `delegate`, `start_session`, `read_session`, `stop_session`; `validate` checks arguments and caps text and titles; bad arguments are a tool result with `isError`, an unknown tool is `-32602`). Every other method that carries an id (`prompts/list`, `resources/list`, `server/discover`, which Qwen Code and Claude Code send) gets JSON-RPC `-32601`, never a dropped connection; a notification gets no reply; batches and lines over 1 MiB are refused. **Calls** (`service.rs`, `AgentTools`): a `tools/call` is parked in a pending table and emitted as the Tauri event `agent-tool-call` (`{callId, sessionId, tool, args}`); the webview answers with `agent_tool_respond(callId, ok, text)` (`agent_tools/commands.rs`), and the text goes back on the agent's connection as the call's result (`isError` when `ok` is false). A call ends with an answer, after `CALL_TIMEOUT` (170 s, since Antigravity gives up on a tool call at 180 s and Qwen Code and Codex at 5 minutes; the agent is told Zorvo did not answer in time), when the agent sends `notifications/cancelled` whose `requestId` equals the call's JSON-RPC id on that connection, or when its session is forgotten or the app exits; each end that is not an answer emits `agent-tool-call-ended` (`{callId}`), and a later `respond` for it does nothing. `AgentTools::start` takes the `emit` and `ended` callbacks (`start_with_timeout` is for tests); `AgentTools::disabled()` has no socket, is used when binding fails and by tests that open no tools, and always returns `[]`. **Handing a session its server:** `servers_for(sessionId, enabled)` issues the token and returns the ACP `mcpServers` entry (`{name: "zorvo", command: <this executable>, args: ["mcp-bridge"], env: [{name, value}]}`), or `[]` when not enabled. `acp_start_session`, `acp_reopen_session`, `acp_import_session` and `acp_fork_session` take `agentTools: bool`; `servers_for_session` reads `Settings.agent_tools` only when the webview asked, so both must be true, and `forget_if_failed` drops the token when the session did not open. `Settings.agent_tools` is described under **Setting** below. The webview's flag is `sessionGetsAgentTools` (`lib/agent-tools.ts`: false for a compare-run session or a delegated one, true for a plain session and a fork), passed by `useAcpEngine`. **Webview:** `hooks/useAgentTools.ts`, mounted by `App` (main window only; a popout would answer twice), answers every `agent-tool-call`, on every path, since an unanswered call costs the agent its own timeout. `lib/agent-tools.ts` holds the pure rules: `parseToolCall`, `resolveAgent` (an exact id, else exactly one agent whose name matches but for case; part of a name never matches, and the error lists the ids), `statusRefusal` (not installed, needs a sign-in), `listAgentsText` and `delegateResultText` (the JSON an agent reads), and the fixed answers `DECLINED`, `NO_SESSION`, `NO_SUCH_HANDLE` and `UNREADABLE`. `list_agents` is answered at once with the agents in use and this session's delegates; the hook is given `agentsInUse`, not every detected profile, so an agent the user took out of use is neither listed nor reachable by `delegate`. `delegate` resolves the agent and then needs a **grant**: memory only, per session, gone after a reload, taken back from the ⋯ menu (**Stop allowing delegation**). Without one the call waits and the session's chat gets a card Zorvo makes itself (`lib/agent-tool-card.ts`, `ActionCard.zorvoTool`; never the agent's own permission request, since Qwen Code and Codex ask none for an MCP tool): the caller, the target, the folder and the task as text with its line breaks kept and every other control or bidi character spelled out, with **Allow for this session** and **Deny**. Several calls that wait in one session share one card that lists every task. Allow records the grant and runs the waiting calls in arrival order through `useDelegation.giveTask(…, { byAgent: true })`; Deny answers each "The user declined." and keeps no grant. `agent-tool-call-ended` (the backend's timeout, the agent's cancel, a stopped session) takes that call off the card, and a card with no call left reads Not answered; a card loaded from a transcript is never pending (`loadTranscript` settles every pending card). The card's answer is routed in `App.tsx`'s `chooseOption` (`agentTools.chooseCard` first, else the engine's `acp_respond_permission`), which a popout's `choose-option` also goes through, and a session with a pending Zorvo card counts as waiting (`isSessionWaiting`). A compare-run session, a delegated one, one an agent opened, or an unknown one is told it cannot use the tools. **Sessions an agent opens (`start_session`).** An independent session is an ordinary session with `Session.openedBy` (`{ sessionId, at }`, kept leniently in `persistence.ts` and `store.rs`, `STATE_VERSION` stays 2): the brief is its first message with no hidden context, it sends no report, it is not selected, and `sessionGetsAgentTools(session, sessions)` is false for it, so it cannot open more (one level), and for any fork of a session that has no tools (it walks `forkedFrom`; a source that is gone cannot be judged, so such a fork has them). The rules are pure, in `lib/agent-tools.ts`: `resolveFolder` takes only a path that is, character for character after one trailing slash, a folder in Zorvo's list and not the caller's own (`ownFolderOf`: its repository when it works in a worktree); nothing is normalised or resolved there, the error lists the other folders' names and never repeats what was asked, and `acp_start_session`'s `ensure_known_workspace` checks again. `otherFolders` is what `list_agents` returns as `folders`, next to `opened` (`openedSessionsOf`); `sessionTitleOf` is the agent's title or the agent and the brief's first line; `openRefusal` holds the limit, `MAX_RUNNING_OPENED` (3) of an opener's sessions in a turn at once. `hooks/useOpenedSessions.ts` opens it through the app's own `startSession` (`focus: false`) and, for `worktree: true`, `createSessionWorktree` from the opener's repository (the agent names no branch or path); in its own folder the new session shares the opener's worktree. Places are counted in a ref (`underWay`) from before anything awaits until the session is listed, so four calls in one tick open three. A request that ended while git made the worktree (the caller was stopped or deleted, the call timed out or was cancelled) starts nothing: `useAgentTools` keeps the opens that run in `opening`, marks one whose `agent-tool-call-ended` arrives, and `open` reads that through `OpenRequest.isCancelled` after the await, removes the unused worktree and frees the place. A worktree that cannot be made, or a `startSession` that throws, opens nothing, frees its place, and returns a reason written for the caller with the error in `detail`, which `useAgentTools` shows the user as a notice and never sends to the agent. `startSession` itself does not wait for the agent: the tool answers `opened` once the session is recorded, so an agent that then fails to start (not signed in, say) leaves a session with the brief back in its composer while the caller was told it opened. In `useAgentTools`, a `start_session` in the caller's own folder joins the same queue as `delegate` (`enqueue`): it runs under the session's grant, or waits on the session's card, which lists every waiting request under its own heading (`toolCardFor`: "For {Agent}:", "New {Agent} session:"). A `start_session` with `folder` never uses the grant: each gets a card of its own (`folderCard`, kept in `folderCards` by card id) with **Allow once** (`ALLOW_ONCE`) and **Deny**, shown even when the session has a grant, and Allow once records none. So one session can show a grant card and folder cards at once, each answered on its own. The chat of an opened session shows `OpenedByLine` in the delegate line's place ("Opened by {Agent} from {Session}", or that the opener is gone). `COMMAND_PATH_CONTEXT` names `start_session` for Pi. **Handles, `read_session`, `stop_session`.** An agent names a session it started by a handle, never by Zorvo's session id: a delegate's handle is its agent's id, derived while its link is open (`handleOf`; a session holds one open delegate per agent, so nothing is stored), and an opened session's is `session-N`, kept in `openedBy.handle` (`nextSessionHandle`, issued in `useOpenedSessions` with the place, so sessions opened in one tick get different ones; `persistence.ts` and `store.rs` keep only a handle of that shape). `delegate`, `start_session` and `list_agents` return it. `ownedByHandle(callerId, handle, sessions)` finds only the caller's own, unarchived session; every other handle (another session's, an archived one, a Zorvo id, a typo) gets the one sentence `NO_SUCH_HANDLE`, so nothing can be told apart. Neither tool shows a card or needs a grant: they only reach what the caller started. `read_session` answers `readSessionText`: the session's state, the newest finished answer of the other agent (cut at `max_chars`, at most `MAX_REPORT_CHARS`), the files it reported changing relative to its folder, and the note that the answer is a quote, not an instruction; never what the user typed there. The messages come from `messagesOf` (`App.tsx`: the loaded transcript, else `loadTranscript` plus what arrived since); an unreadable transcript answers `UNREADABLE`, never the cause. `stop_session` calls `stopTurn` (`handleInterrupt`, the Stop button's path) for a session that works or waits for an answer and says `{ stopped: true }`; an idle one gets `{ stopped: false }` and nothing is called. It ends the turn only: the session, its delegate link and its worktree stay. `COMMAND_PATH_CONTEXT` names both for Pi. **Setting:** `Settings.agent_tools` is on unless the state says `false` (`lenient_on`, a manual `Default`; `persistence.ts` reads `agentTools !== false`), with a switch in Settings → Agents (`components/settings/AgentToolsSetting.tsx`); it applies to sessions started or reopened afterwards. **Command path:** Pi through `pi-acp` ignores `mcpServers` (its tools are `read`, `bash`, `edit` and `write`; ACP has no capability that says so), so it reaches the same tools from its shell. `path.rs`: `COMMAND_PATH_AGENTS` holds the registry ids a spike showed ignore the server (today `pi-acp`), `path_for(profileId)` gives `ToolsPath::Mcp` or `Command`; an agent leaves the list when a later version starts the server. `tools_for_session` (`agent_tools/commands.rs`) is the one place that decides what a session gets: nothing unless the webview asked and the setting is on, then the `mcpServers` entry, or, on the command path, `[]` plus `launch_env_for`'s three variables (`ZORVO_MCP_SOCKET`, `ZORVO_MCP_TOKEN`, `ZORVO_TOOLS`, the executable's path), never both. `with_tools_env` puts them last in `AcpLaunch.env` and removes any earlier entry of the same name, so a registry entry cannot stand in for them. The token is per agent process there, since the environment is. A fork lives in its source's process and cannot be given an environment, so it gets the MCP entry whatever the agent (`servers_for_session`), which a command-path agent ignores: a forked Pi session has no tools. `zorvo tools [<tool> [<json>]]` (`cli.rs`, a third branch in `main.rs`) sends the token line and one `tools/call` and prints the answer: the text on stdout and exit 0, or on stderr and exit 1 for an error result, a refused token or no answer (`Zorvo is not reachable from this shell.` when the variables or the socket are missing); the words after the tool are joined before parsing, so JSON an agent forgot to quote still works, and anything that is not a JSON object exits 2 with a quoting hint. With no tool, or `--help`, it lists the tools with an example each. It holds no logic and never prints the token. Killing the command closes its connection, which ends the waiting call. **The app never opens from an agent's environment:** when any of the three variables is set and the first argument is neither `tools` nor `mcp-bridge`, `main` prints the usage and exits 2 (`is_agent_environment`, `refuse_app_start`). Pi ran `zorvo --help` after a failed call, which opened a second Zorvo that never exited. The cost: `pnpm tauri dev` started by an agent inside a command-path session does not start until the three variables are unset, and the message says so. **Telling the agent:** the session answer carries `toolsPath` (`mcp`, `command`, or absent), validated in `useAcpSessions.ts`. `useAcpEngine` keeps the command-path sessions that are due the context (`toolsContextDueRef`, filled when a session starts, reopens or imports, emptied on stop) and `prompt()` puts `COMMAND_PATH_CONTEXT` (`lib/agent-tools-context.ts`, the wording Pi acted on in the spike; `withToolsContext` puts it before a message's own hidden context) ahead of the first message the agent takes, so a refused prompt leaves it due; `acp.prompt` returns on write, so a turn that carried the context and then failed puts it back (`toolsContext` on the last prompt, read in `onTurnEnd`), and Try again sends it again. It is never shown in the chat and nothing is written into the agent's config or the project. The context names all five tools. Tests: `src-tauri/tests/it/agent_tools_socket_test.rs`, `agent_tools_service_test.rs`, `agent_tools_cli_test.rs` (the real binary as `zorvo tools`) and `agent_tools_e2e_test.rs` (the fake agent as an MCP client through a real bridge process, and running `zorvo tools` from its environment).

**Delegation.** A session (A) hands a task to another agent's session (B) and gets B's answer back. Three ways in, one path: the top bar's ⋯ menu (`DelegateDialog`, `useDelegateDialog`), an `@Agent task` mention at the start of the composer (`delegationMentionOf`, `mentionBlockedReason`), and the agent itself through the `delegate` tool (see **Agent tools**); all end in `useDelegation.giveTask`. The link is `Session.delegatedFrom` on B (`DelegationLink`; an open link has no `endedAt`), so nothing else is stored. **One open delegate per agent:** `openDelegatesOf(A)` lists A's (oldest first), `openDelegateOf(A, agentId)` finds one agent's, `sourceOf` finds A even when archived, and a delegated session can never delegate (one level). `lib/delegation.ts` is pure. `taskRoute` decides where a task for an agent goes: `start` (no open delegate of that agent), `follow-up` (its delegate is idle: the task is that session's next prompt), or `blocked` (the delegate works or waits for an answer: "… is still working on the previous task."; a delegated source; a source with no messages, with the empty reason; a busy source, unless its own agent asks, `isSourceBusyAllowed`). `delegateBlockedReason` is the route's reason (source-only checks when no agent is named, as for the menu item). `sendBlockedReason` blocks only B, while A works on B's report; A's Send is never blocked by a delegate, since A may hold several and the user steers it. `buildDelegatePrompt` is one line of hidden context naming the handoff file, `reportMessage` quotes B's last complete answer with `> `, cut at `MAX_REPORT_CHARS` (20,000), with the files B reported changing, all through `escapeVisible`, and `followUpSummary` is the composer's line for a mention that goes to an existing delegate. `hooks/useDelegation.ts` does the effects. `giveTask(sourceId, agentId, task, { byAgent })` returns what happened (`started`, `sent`, or a reason) and never raises a notice; `start` wraps it for the dialog and the mention and turns a refusal into a notice. A start writes A's conversation as a fork-style handoff (`write_fork_handoff`) and starts B in A's folder and worktree with the task as its first message; with `byAgent` the handoff stops before A's unfinished reply (the one that holds the tool call), B is started with `focus: false` and is not selected. Guards keep the route honest between renders: a further task holds its delegate in `sendingTo` from before the send until the delegate is seen busy or its turn ends, so two tasks for one idle delegate in the same tick do not reach the same turn (busy is React state and is not observable in that tick); and three more: a start is held in `starting` (by source and agent) from before the handoff is written until the new session is listed, so a second task for the same agent in the same tick is refused, not started twice; a follow-up is refused while that delegate's last report has not reached A (`isHandingOver`), since the task would become B's last message and the waiting answer would be lost; and a delegate whose session is `terminated` gets its link ended and the task starts a new one. A failure inside Zorvo comes back as `isInternal` with the error in `detail` for the user's notice, and an agent is told only "Zorvo could not do that." A follow-up is sent with `send(B, task, …, { delegationTask })` (the message reads **Task from {A's agent}** in B's chat, `MessageRow`) and B's link takes the new task, which the next report quotes. **Reports wait their turn:** `onTurnEnded` (fed by the engine's turn ends) puts B's finished turn in `pending`; the drain sends a report only when A is neither in a turn nor waiting on the user, at most one per source per pass (taking it starts A's next turn), oldest first, as a user message marked `delegationReport`. It is given back into A's composer, with a notice, only when A is idle and still cannot be prompted (not running, agent removed, sign-in needed) or when the agent refuses it. B's Send is blocked while its report is queued ("…'s report waits for … to finish.") or being sent (`delivering`). Same-tick decisions read refs, outcomes are memory only, and `end` closes the link and drops a queued report. `viewsFor` gives a source one status line per open delegate (`DelegationStatusLine`, oldest first) and a delegate its own (`DelegatedFromLine`); the Delegate dialog shows where the task goes in place of the model, effort and mode chips for an agent that already has a delegate (`DelegateAgentChoice.hasDelegate`; an existing session keeps what it runs on, so no pick is sent), the ⋯ menu lists **End delegation to {Agent}** per delegate when there are several, and archiving A ends them all. Not built: a delegate in another folder or its own worktree, nested delegation.

**Qwen Code's questions.** Qwen's `ask_user_question` tool is not standard ACP elicitation: it arrives as a normal `session/request_permission` whose `toolCall._meta` has `qwenInteractionKind: "user_question"` and `qwenQuestions` (each `{ question, header, options: [{ label, description }], multiSelect }`; one to four questions, two to four options), and it expects the response's usual `outcome` plus a top-level `answers` object (question number as a decimal string "0".."3" to a string; a multi-select question's picks joined with ", ", free text as typed; Qwen's `normalizeTrustedUserAnswers` skips empty strings). Cancel is the reject option (`wasAnswered` false). `lib/user-questions.ts` `parseUserQuestions` validates the shape when the request arrives (`applyPermissionRequest` sets `ActionCard.questions`; anything that does not parse stays a plain card), cleans the text with `escapeVisible` and cuts it, since a label is also the answer. `ActionCard` shows `UserQuestionFields` (radios, or checkboxes for a multi-select question, plus **Other** with a text box) and holds the picks in component state, so an answer that did not go through keeps them when the card is asked again; they are never put on the card, in the transcript, or in a log. **Submit** (the card's allowing option) is disabled until every question has an answer and sends `answers` through `onChoose(optionId, answers)` → `chooseOption` (only for a card with `questions`) → `respondPermission` → `acp_respond_permission`; the popout bridge's `choose-option` action carries them too. The Rust side builds the response: `acp/permission_response.rs` `permission_response` takes at most 4 answers, keys "0".."3", non-blank values of at most 2000 characters, and refuses answers on a cancel, with errors that never repeat a typed value; `AcpManager::respond_permission` checks before it looks up the connection, so a refused answer leaves the request open. The fake agent's `user-question` prompt sends such a request and `FAKE_ACP_QUESTION_LOG` records the reply.

**Stalled agent notice.** While a turn runs, `components/chat/AgentStallNotice.tsx` (under `WorkingIndicator`) shows a soft warning with Stop, never persisted. `lib/agent-stall.ts` holds the rules and copy: failure counts from ACP (Qwen Code's `executionLifecycle` metadata, Codex's `_meta.codex.error.willRetry`), kept per session by `hooks/useAgentFailures.ts` (fed from `useAcpEngine`'s `onUpdate`, never during a load replay, cleared on agent news, turn end, stop and exit), else "hasn't sent anything for N minutes" after 60 s without news (never while a tool runs). Qwen reports a failed request without the error, so `acp_qwen_last_api_error` (`acp/qwen_log.rs`) reads the newest `qwen-code.api_error` of the turn from the tail of Qwen's own `projects/*/chats/<id>.jsonl` (validated ACP id, never logged). Zorvo does not opt into the AIR `sessionFailure` extension, since that would drop the final error text `turnEndNotice` shows. Popouts get `failures` in `SessionLiveStatus`.

**Environment.** A Finder-launched app has no shell PATH, so `env_resolver.rs` reads the user's login-shell environment once (warmed at startup) and every spawn uses it. `get_agent_profiles(refresh: true)` re-reads it (with the registry and `npm`), and `refresh_login_env` re-reads only it, for the sign-in checks.

**Persistence.** `store.rs` writes `state.json` and `transcripts/<id>.json` atomically under `~/Library/Application Support/xyz.zorvo.desktop/`. Each transcript write is the whole file, so `useTranscripts` spaces them by the size `save_transcript` returns (`transcriptSaveInterval`: 1 s up to 128 KiB, then about 128 KiB a second, at most 10 s apart); `useAcpEngine` calls `saveSoon` on a turn end, a permission or elicitation request and an exit, which brings the waiting write forward to 100 ms (100, not 0: the write reads `transcriptsRef`, which follows the render). A tool's diff is kept as the rows the chat shows (`ToolDetail` `{ kind: 'diff', path, isNewFile, rows }`, made once by `diffDetail` in `lib/diff-rows.ts` when the update arrives), never as the whole file before and after that ACP sends with every edit: those made a long session's transcript tens of megabytes and froze the page on each save. `normalizeTranscript` turns a diff an older version saved with `oldText`/`newText` into rows on load. Frontend validation/normalization of loaded state is in `src/lib/persistence.ts` (`STATE_VERSION`); `data_migration.rs` copies data once from the old `com.agentdesktop.app` folder. On load the UI calls `end_orphaned_sessions`, because a webview reload leaves backend agents running that the new UI does not know.

**Path checks.** Every backend command that reads or runs in a folder from the UI must first call `files::ensure_known_workspace` (canonicalized, checked against the store's known workspaces). Follow this in any new command.

**Popout windows.** A session can open in its own window (`index.html?session=<id>&popout=1`, see `lib/window-mode.ts`). The main window is the single writer: it parses agent output and persists state; popouts only render snapshots and forward actions (`lib/popout-bridge.ts`), so two windows never write the same files.

**Fork, rewind, worktrees.** Fork uses the agent's native ACP fork when available, otherwise a handoff file (`fork_handoff.rs`, `lib/fork-handoff.ts`) the new agent is told to read. Worktree sessions get an `agent/<title>` branch under the app data dir's `worktrees/` (`worktrees.rs`), made from HEAD or a local branch picked in the folder list. `branches.rs` lists local branches and switches a draft's folder to one (`useBranchPicker`); `switch_branch` refuses while any open ACP session (`AcpManager::session_folders`) works in the same checkout, and every branch name from the UI is checked against `refs/heads/` before it reaches git. Git changes/commits are in `changes.rs` and `diff_stats.rs`; PR data comes from the user's own `gh` (`pull_requests.rs`).

**Compare agents.** In a repository the draft's Agent chip (`AgentMultiPicker`, `useCompareDraft`) ticks up to `MAX_COMPARE_AGENTS` agents; an agent that needs an install or a sign-in cannot be ticked. `useCompareRun.startRun` makes the worktrees one at a time (the repository's index is locked while one is made), points the attachments into each, and starts every session with the same `compareRunId`, each agent in its safest mode through `applySafeMode`. A run that ends with one session gets no id and is a normal session. Nothing about a run is stored but that id on each session: `lib/compare-run.ts` derives it (`compareRuns`, oldest first), and a group shows while two or more listed sessions share the id. So there is no record to migrate or to fall out of step with the sessions (`STATE_VERSION` stays 2), and a Pick needs no bookkeeping: the winner keeps its id, is left alone and is a plain session again. `components/compare/` is the panel, in the chat's place: `useCompareRunRows` loads every session's chat, `rowFactsOf` and `rowStatus` make each row's one word, and its numbers are `session_diff_stats_since` against `worktree.startCommit`, untracked files included. A row reads them through `session.cwd`, never `worktree.path`: from a subfolder the root is not a known workspace, and `diff_stats_since` finds the root itself. It reads them again on `runVersion` and whenever its own status changes, since a Stop only cancels the turn (`handleInterrupt`; a cancelled turn end fires no `onAttention`, so `runVersion` stays) and an agent dying between turns ends no turn. Pick always asks first, in a confirm bar at the panel's bottom that names the agents it would stop mid-turn (`pickQuestion`, `stopsLine`), and is off for a row whose changes are known to be empty (loading or unreadable numbers leave it on); it then archives the others one at a time, and their worktrees stay; an agent that cannot be stopped stays in the run, with a notice. A run that goes away while its panel is open, with one listed session left, selects that session (`lastOfRun`) in the same render, in `App.tsx`, so no draft mounts; with another session on screen the selection stays. **Sign-in.** A run's refusal never takes the `authRequest` slot when it arrives: `App.tsx` sees `isInRun` and calls `keepSignIn`, so several refusals at once cannot fight over one slot and no panel covers the run. It is kept in memory on the row (`signInNeeded`, which reads Needs sign-in) until the row is opened, and only then does `takeSignIn` ask through `signIn.handBackKept`, since only then does its composer show. `dropSignIn` ends it once the message goes out or the user changes it; memory only, so after a restart the row reads Stopped. `watchedRuns` holds the runs started in this window, the only ones that notify, once, when they settle; `awaitsRunNotice` holds back each session's own notice meanwhile.

**Diff comments.** The user comments on lines in `DiffView` (the full review, which opens in the chat's place from the top bar's diff chip or the Changes tab; Shrink, or Add to message, brings it beside the chat so the composer shows) or in the inspector's Changes tab, adds them to the composer, reads or edits the text, and presses Send: there is no other way out for a comment. A comment belongs to one session (`Session.reviewComments`, `store.rs`'s lenient per-item reader, `lib/persistence.ts`; `STATE_VERSION` stays 2) and is checked only against the diff it was written on: its `target`, `side` and `line`, by `commentStatus` (`lib/review-comments.ts`). The row at that line with the same `lineHash` is Current; a row that differs or is gone, or a file the target no longer lists, is Outdated; a diff cut before or on that line, or a failed read, is Unknown; another target is Not in this diff. Add N counts Current and Unknown comments that are neither In message nor Sent; an Outdated one has its own Add, and its text says the line is gone. A comment never moves: about a third of this repository's non-blank lines repeat within their file, so searching for the text would attach a comment to the wrong line and the message would confirm it. `lib/review-comments.ts` also words the message; quotes and paths have control characters, U+2028, U+2029 and bidi controls turned into visible escapes, so the user reads what the agent reads, and the body stays verbatim. `session_diff_targets` gives the root and the folder's prefix, so paths are relative to the agent's folder and a file outside it gets its absolute path. `session_file_diff` takes `since` for `DiffTargetId` `'start'` (**Start of this worktree**), offered with `worktree.startCommit` and the default only for a session with a `compareRunId`; a compare row's numbers open it (`onReview`). The controls are opt-in through `FileDiff`'s `review` prop, which `DiffView` and `ChangesPanel` pass for a session on screen, both through `hooks/useFileReviews.ts` (the file reads, the statuses, the `CommentAdder` and each file's `FileReview`), so drafts have none. The Changes tab lists what Commit would take, so its comments are always on `head`, and its bar lists only those; a comment on another target stays the full review's, which can show that target. `hooks/useReviewComments.ts` holds the session's comments and the boxes being written. `hooks/useReviewMessage.ts` holds one slot, `{ sessionId, commentIds, lastTarget }`, since one `ComposerDock` serves every session and keeps its text across a switch, so Zorvo must remember whom added comments are for. The slot is in memory only because composer text is too: after a restart an In message comment is a plain comment. It lifts when the composer is emptied or `ComposerHandle.restore` replaces the text (a rewind, or a worktree or run that failed to start), since the comments go with it. `ComposerHandle.giveBack` keeps the composer's text, so it never lifts a slot. Text with comments that comes back keeps its owner: `lastSends` keeps, per session, the text and target of its last send that held comments, by session since one message may wait while another session sends, and drops an entry when its text arrives or its session goes away. `restore` of exactly that text re-arms the slot for that session with no comment ids. `giveBack` does the same through `onGivenBack`, which gets the returned text, not the text it joined, when that holds the message as a whole block, since `useUnsentMessages` joins several; a slot already set for the session keeps its comment ids. While a slot belongs to another session, nothing is given back to this one (`isHeldFor`): `useUnsentMessages` keeps the message and delivers it on the render after the slot lifts, and `useAgentSignIn` routes its direct calls through the same gate, so a held refusal opens no `pending` and is not resent on its own after the sign-in. Otherwise A's text would join B's comments, whose note points to B, and go to B's agent. Send from a re-armed slot marks nothing new. While the slot is set and the composer holds text, Send is blocked everywhere but the slot's session, which `hooks/useReviewWiring.ts` also blocks when it cannot continue, since Send would otherwise start a new session (`reviewOwner`, `composerNote`; the note names a compare run's session by its agent, as all of a run's sessions share one title). A compare run's panel hides the composer and does not unmount it (`hidden` in `App.tsx`), so a look at the panel keeps the message; `insertPaths` drops what comes in meanwhile, so nothing goes into a message nobody can see, and the restores wait for the composer to show. `RemovedAgentPanel` shows in the composer's place the same way (`isComposerHidden`), so a look at a removed agent's session keeps the message too. A hidden composer takes nothing: a message that comes back to a removed agent's session, whatever the session's status, waits (`isMessageHeldFor`, which `useAgentSignIn` also reads before it resends), and a rewound one waits in `pendingRestoreRef` under its session id, until Add brings the composer back. Zorvo marks Sent rather than guessing what reached the agent: `acp_prompt` returns on write, stop reasons differ per agent, and matching text in an editable box breaks on one typo. So `sentAt` says Send was pressed, not that the agent acted; a Sent comment stays with **Add again**, keeps its status so a line the agent fixed reads Outdated, and **Clear sent** removes them. Editing an In message or Sent comment makes it plain, and the text already in the composer or the chat stays.

**Threading rule for Tauri commands.** Commands that touch the filesystem, the login shell or a child process are `#[tauri::command(async)]` so they don't freeze the window. `send_input` stays sync so a terminal's keystrokes reach the PTY in order: async would run them on a thread pool where they could arrive out of order. `end_orphaned_sessions` is sync for the same reason (sync commands run on the main thread in the order the webview sent them, so its list of orphans is taken before any later start registers); it only lists sessions there and ends them on a thread of its own.

## Testing conventions

- Frontend tests live in `src/test/` (Vitest + Testing Library, jsdom). `src/test/setup.ts` fakes Tauri `invoke`, including an in-memory store seeded via `window.__FAKE_TAURI_STORE__` and canned ACP responses; agent profile fixtures are in `src/test/fixtures/agents.ts`.
- Rust tests are in `#[cfg(test)]` modules and `src-tauri/tests/it/` (one binary; a new file needs a `mod` line in `main.rs`, which a test checks).
- `src/test/tauri-contract.test.ts` checks the wiring the fake backend and the Rust tests both miss, by reading the source of both sides (the frontend with the TypeScript compiler API, the Rust with a small scanner in `src/test/helpers/tauri-contract.ts`). Every `invoke('name', { keys })` must name a command in `generate_handler!`, pass only keys that are parameters of its `#[tauri::command]` fn (camelCase of the snake_case name) and all of its non-`Option` parameters (a key passed only inside a conditional spread is allowed but does not count as passed). Every `listen`/`once` event must be emitted by Rust or by the frontend, and every event Rust emits must be listened to or listed in `EVENT_ALLOWLIST` with a reason. A call whose command name is not a literal goes in `NON_LITERAL_CALLS` with the commands it can reach; a stale entry fails too. When it fails after you add a command, an argument or an event, fix the name or key, or the table, not the check. It does not check argument types or values. `helpers/tauri-contract.test.ts` tests the extractors and each assertion on small inline snippets. The scanner refuses `rename_all` and destructured parameters, so a command that needs either needs the scanner taught first.
- Agent worktrees under `.claude/` contain copies of the repo; Vitest and ESLint both exclude `.claude/**`.

## Working in worktrees and keeping disk use down

Parallel sessions each work in their own git worktree under `.claude/worktrees/`; two sessions in the main checkout share its files and its current branch. `node_modules` costs almost no disk there (pnpm clones its store's files on APFS, so `du` overstates it); the Rust `target` folder is what costs real disk (about 1.5 GB) and build time.

- **One shared Rust target.** On the maintainer's Mac an untracked `.cargo/config.toml` at the repo root (hidden through `.git/info/exclude`) holds `[build] target-dir = "/Users/mac/Library/Caches/zorvo-target"`. Write the absolute path: cargo does not expand `~`, and would build into a folder literally named `~` inside the repo. Cargo reads the file from every worktree below the repo folder, so a new worktree compiles only the `zorvo` crate (about 35 s) instead of every dependency (a cold build took about 9 minutes). Leave the file alone: `git clean -x` would remove it, and every worktree would silently go back to its own `target`. Builds from several sessions queue on cargo's file lock, and `pnpm clean:rust` empties the shared folder for all of them, so don't run it while another session builds. Deleting the folder is safe: the next build recreates it. Without the file (CI, another machine, a worktree outside the repo folder) each checkout builds its own `target`; run `pnpm clean:rust` there once its PR has merged or its session is done.
- **Run only what the change needs.** `pnpm lint` and `pnpm test` for anything under `src/`. Add `cargo fmt --check`, `cargo clippy --all-targets -- -D warnings` and `cargo test` only when `src-tauri/**` changed (CI also runs them for `package.json`, `pnpm-lock.yaml` and `.nvmrc`). A docs, site or copy change needs no cargo, and no new worktree either when no other session works in the main checkout: use a branch there.
- **Review before the push.** Review the diff and fix what it finds before pushing (Claude Code: `/code-review --fix`), so CI runs once on a reviewed change.
- **After a merge,** update local `main` and run `git worktree list`: `git worktree remove` any worktree left for a merged branch. The app's auto-archive on PR close (on for the maintainer) archives the session and, per the app, removes the worktree it made unless that holds uncommitted changes. A worktree made with `git worktree add` is yours to remove.

- `src/styles/globals.css` is the source of truth: its `@theme` block holds dark values and generates Tailwind utilities (`bg-surface-2`, `text-fg-muted`, `border-border-strong`); a `prefers-color-scheme: light` block overrides them. - UI copy: sentence case, short declarative sentences, address the user as "you", name the agents rather than saying "AI". See `docs/design-system/README.md`.

## Project rules

- The app never asks for or stores API keys/tokens; agents sign in with their own tools. The CSP (`tauri.conf.json`) allows only the local IPC bridge — the webview makes no network requests. The backend makes only three kinds: it reads the ACP registry, on **Install** it downloads from the hosts that install needs (listed in the README's privacy section), and it checks `latest.json` in this repository's latest release for a newer Zorvo (shortly after start, then daily) and downloads that update from GitHub when the user clicks **Update & restart**. It also runs the user's own `gh` (pull requests, and the GitHub connection's sign-in state), which makes its own requests; Zorvo sees only what `gh` prints and stores none of it. It also listens on a private Unix socket in the app data dir (or a short `/tmp` path) for its own `mcp-bridge` process (see **Agent tools**); that is local and uses no network.
- Prefer a focused hook in `src/hooks/` or a helper in `src/lib/` over growing `App.tsx`.
- Conventional Commits (`feat:`, `fix:`, `refactor:`, `docs:`, `test:`, `chore:`, `ci:`); branches `feat/…`, `fix/…`, `chore/…`. Add a line under `Unreleased` in `CHANGELOG.md` for user-visible changes.
- Release: bump the version in `package.json`, `src-tauri/Cargo.toml` and `src-tauri/tauri.conf.json`, roll the changelog, then push a `vX.Y.Z` tag; the Release workflow builds a universal macOS app, then `node scripts/sign-release.mjs vX.Y.Z` on your Mac signs the update and fills a draft release.
- xterm 6 broke under esbuild's syntax minifier (Vite 6). Vite 8 builds with Oxc, which keeps it working; `xterm-release-build.test.ts` builds xterm as the release does and checks the terminal still answers. Don't remove it, and run it after changing the minifier or the build target.
